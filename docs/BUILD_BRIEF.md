## 목표와 기준 문서

CS Class의 1차 목표는 실제 학생·교사 계정으로 로그인하고, 교사가 담당 반의 이번 수업을 지정하며, 학생이 작은 활동을 수행하고 서버에 저장한 뒤 재접속하여 본인의 작업을 복원하는 것입니다. 예시 데이터만으로 화면이 움직이는 상태는 이 목표의 완료가 아닙니다.

- 제품 요구사항은 [PRD](../PRD.md), 시각 기준은 [DESIGN](../DESIGN.md), 개발·검증 절차는 [AGENTS](../AGENTS.md), 실행 방법은 [README](../README.md)를 따릅니다. 최신 논의 위치는 [HANDOFF](HANDOFF.md)입니다.
- 확정 정책을 다른 문서에 중복 복사해 변경하지 않습니다. 모순이 발견되면 최신 사용자 결정과 근거를 확인하고 관련 문서를 함께 정리합니다.
- 기존 Git 변경을 보존하고 실제 코드·환경부터 확인합니다. Next.js 코드를 작성하기 전에 설치된 버전의 `node_modules/next/dist/docs/`에서 관련 안내를 읽습니다.

## 확정된 범위와 후속 작업

**확정:** 실제 로그인·반별 권한·수업 지정·개인 작업 저장·복원이 1차 목표입니다. PRD의 비밀번호·세션·교사 초기화 정책과 학습 완료 규칙을 유지합니다. AI 연결은 이후로 미룰 수 있습니다. 월 4만 원은 사용자가 수용한 참고 예산이며 특정 유료 요금제 구매 승인으로 해석하지 않습니다. Firebase `cs-class-f74c4` 사용은 별도로 승인받았습니다. 사용자는 무료로 사용할 AI API가 별도로 있다고 했으며 공급자·키·사용 조건은 아직 확인하지 않았습니다.

**1차 구현 범위:** 중앙 집중형 로그인, 학생·교사 대시보드, 반별 수업 공개·이번 수업 지정, 계정 관리에 필요한 동작, 검증용 수업, 서버 저장·복원까지 한 흐름으로 완성합니다. 기존 공개 홈 스타일과 학생 홈의 `이번 수업 + 열린 수업`을 유지합니다. 실제 사용자 계정 생성·기존 자료 이관의 대상은 별도로 확인합니다.

**후속 연결:** 첫 검증에는 EntryJS 대신 간단한 순서 배열 실습을 사용하고 EntryJS·AI는 이후 연결합니다. Q&A와 정식 콘텐츠는 후속 연결이며 Q&A의 이미 합의한 답변·해결 정책은 유지합니다. 자유시간 자동 처리·범용 수업 편집기를 1차 필수 구현 목록에 넣지 않습니다. AI 기능이 없어도 기본 활동의 검증·제출·완료가 동작하게 설계합니다.

**검증용 수업 — 사용자 선택 확정:** 개념 2개, 퀴즈 3문항, 간단한 순서 배열 실습 1개로 전체 흐름을 검증합니다. 저장·이어하기·개념 자동 완료·오답 재도전·실습 자유 이동·검증 후 제출을 확인합니다. 설명·문항과 검사 조건은 `src/lib/classroom/catalog.ts`와 서버 학습 로직에 구현했으며 정식 교과 콘텐츠를 완성했다는 뜻은 아닙니다. EntryJS의 직렬화·편집기 생명주기·자동채점 검증은 이후 별도 연결 단계에서 수행합니다.

## 구현과 검증 순서

1. **공통 규칙을 먼저 정의합니다.** 계정·역할·반·수업·활동·진행 기록·초안·제출본의 관계, 서버 권한, 저장 충돌·실패 처리와 화면에서 사용할 데이터 형식을 정합니다. 필요한 실제 서비스 대상과 설정 항목도 확인합니다.
2. **하나의 흐름을 먼저 연결합니다.** 테스트 계정의 실제 인증 → 반의 공개 수업 조회 → 작은 작업 저장 → 세션을 다시 시작한 뒤 서버에서 복원을 검증합니다. 로컬 임시 저장이나 모의 인증만 확인한 결과와 구분합니다.
3. **로그인·학생·교사 화면을 완성합니다.** 공통 규칙을 사용해 확정된 로그인 정책, 수업 지정·전환, 활동·완료, 담당 반 내 계정 관리 동작과 오류 상태를 연결합니다.
4. **사용 흐름과 권한을 통합 검증합니다.** 아래 완료 조건을 실제 브라우저·서버 요청·DB 권한 경로에서 확인합니다. 구현 중 필요한 검증도 각 단계에서 수행하며 마지막에 몰아두지 않습니다.
5. **근거와 남은 한계를 인계합니다.** 테스트 결과, 확인한 화면, 실제 연결 여부와 남은 설정을 보고합니다. 서비스 연결·배포에 별도 확인이 필요하면 검토 가능한 구현·설정안을 먼저 준비합니다.

## 에이전트 분담 — 구현·통합 검증 완료

사용자는 **메인이 공통 기반·통합을 맡고, 이후 학생·교사 화면을 서브에이전트 2명에게 나누는 방식**에 동의했습니다. 이후 구현 승인을 받아 두 담당 에이전트의 구현·개별 검증까지 수행했습니다. 메인이 공통 변경을 통합했고 최종 lint·typecheck·build와 전체 E2E 27개를 통과했습니다. 실제 허용 Google 계정으로 로컬에서 로그인해 교사 대시보드에 진입한 결과도 사용자와 브라우저에서 확인했습니다.

- 메인은 공통 데이터·인증·권한·저장 구조와 공통 컴포넌트, 최종 통합을 담당합니다.
- 공통 기반이 갖춰진 뒤 학생 화면과 교사 화면을 각각 한 에이전트에 분담합니다. 같은 공유 파일을 동시에 수정하지 않도록 아래 담당 범위를 사용하며, 실제 분담 시점의 코드에 맞춰 경계를 확인합니다.
- 화면 담당자는 공통 API나 권한 정책 변경 필요성을 메인에 전달합니다. 독자적으로 두 번째 인증·저장 체계를 만들지 않습니다.
- 구현이 끝난 작업에 대해 별도 검토 단계를 둡니다. 별도 검토 에이전트를 쓰더라도 판단 근거는 테스트 결과·실제 화면·재현 가능한 실패이며, 에이전트의 동의만으로 통과시키지 않습니다.

## 공통 규칙을 전달하는 형식

공통 계약은 [types.ts](../src/lib/classroom/types.ts), [client.ts](../src/lib/classroom/client.ts), [progress.ts](../src/lib/classroom/progress.ts)에 구현되어 있습니다. 세션 공급자·탐색 보호와 서버 API를 두 화면이 함께 사용합니다. 아래는 실제 계약을 해석하는 기준이며 서비스 운영 검증 완료를 뜻하지 않습니다.

| 개념 | 두 화면이 동일하게 해석할 규칙 |
| --- | --- |
| 사용자·반 | 학번 같은 표시 식별자와 서버의 사용자 식별자를 구분. 현재 역할·담당 반은 검증된 서버 정보에서 받고 화면이 임의로 권한을 선언하지 않음 |
| 열린 수업·이번 수업 | 공개된 수업의 집합과 교사가 우선 안내하는 수업을 구분. 이번 수업을 바꿔도 이전 공개·학생 작업은 보존 |
| 활동·진행 | 수업 안에서 안정적인 활동 식별자를 사용. 응답·미응답·오답·해결을 구분하고 서버가 확인한 기록으로 학생·교사 진행을 함께 표시 |
| 초안·제출본 | 편집 중 작업과 성공적으로 제출한 작품을 구분. 검증은 작업 버전에 연결하고 검증 후 내용이 바뀌면 재검증. 새 제출이 성공하기 전 기존 제출·완료는 보존 |
| 저장 상태 | 미저장 변경·저장 중·저장 완료·저장 실패를 학습 완료 상태와 구분. 요청을 보낸 시점이 아니라 서버 확인 후 저장 완료로 표시 |
| 오류·재시도 | 인증 만료·권한 부족·일시 통신 오류·버전 충돌을 구분. 재시도가 중복 제출을 만들거나 이전 저장이 최신 작업을 조용히 덮어쓰지 않게 처리 |

**분담 때 적용한 공통 준비 조건:**

1. 세션·반·수업·학생별 진행·작업·제출을 읽고 변경하는 공통 함수와 데이터 형식을 전달할 수 있습니다.
2. 로그인과 권한 실패, 빈 데이터, 저장 성공·실패·충돌 시 응답과 화면 표시 기준이 정리되어 있습니다.
3. 공통 레이아웃·색·글꼴·버튼·입력·다이얼로그·저장 상태 표시와 테스트 데이터 사용법이 준비되어 있습니다.
4. 실제 연결된 기능, 에뮬레이터에서만 확인한 기능, 미연결 기능을 구분합니다. 화면 개발용 모의 데이터는 표시·테스트 목적에 한정하고 실제 인증·저장의 완료 근거로 쓰지 않습니다.
5. 아래 파일 담당 범위를 전달하고 공통 변경 요청을 조정할 메인이 정해져 있습니다. 자격 증명을 확보하지 못한 부분은 필요한 실제 연결 검증이 남아 있음을 표시합니다.

```text
개념 2개·퀴즈 3문항·순서 배열 실습 1개의 콘텐츠와 필수 완료 조건을 공통으로 제공한다.
위 준비 조건을 확인한 뒤 학생·교사 담당자에게 실제 담당 파일과 계약을 전달한다.
공통 계약 변경 요청은 두 화면의 영향을 확인해 반영하고 변경된 계약·검증 범위를 함께 알린다.
테스트 계정의 저장·재접속·다른 계정 접근 거부, 초기화·세션 정책을 실제 경로로 검증한다.
화면 통합 후 lint·typecheck·build·E2E와 실제 UI를 확인하고 결과·미검증 항목을 인계한다.
필요한 실제 서비스 대상과 설정은 확인하되 구현 승인을 배포·실자료 변경 승인으로 확대하지 않는다.
```

### 학생 담당 — 대시보드와 검증용 수업

```text
목표: 본인의 이번 수업 확인 → 학습 → 저장 → 재접속 후 이어하기를 제공한다.
소유 범위: src/app/student, src/app/classroom, src/components/classroom.tsx,
  학생 전용 신규 컴포넌트·스타일 모듈·분리된 학생 흐름 테스트.
메인이 제공한 공통 세션·수업·저장 함수를 사용한다. 별도의 인증·DB 연결을 만들지 않는다.
공통 app-shell·ui·전역 CSS·데이터 계약 변경은 메인에 요청하며 직접 동시에 수정하지 않는다.
화면 구성은 DESIGN과 확정한 세부 결정을 따른다. 제안만 남은 표시·운영 규칙은 승인된 것으로 구현하지 않는다.
샘플의 개념 자동 완료, 전체 문항 후 오답 재도전, 선택 힌트, 실습 자유 이동을 연결한다.
순서 배열은 포인터와 키보드로 모두 완료할 수 있어야 한다.
검증한 작업 버전의 제출 성공 후 완료를 표시하고 제출본과 편집 중 초안을 구분한다.
수업 전환은 미저장 변경의 저장 성공을 확인한다. 실패하면 작업을 유지하고 재시도를 제공한다.
확인: 이어하기, 퀴즈 중간 이탈, 저장 실패, 검증 후 편집, 재제출 실패, 좁은 화면·키보드·콘솔.
공통 서버 오류나 누락 계약은 재현 조건과 함께 메인에 알리고 가능한 독립 UI 작업을 계속한다.
인계: 변경 파일, 구현한 흐름, 실행한 검사와 결과, 실제/모의 연결 구분, 남은 문제.
```

### 교사 담당 — 반별 수업 운영

```text
목표: 허용된 반의 수업을 지정하고 학생 계정과 합의된 학습 정보를 확인한다.
소유 범위: src/app/teacher, 교사 전용 신규 컴포넌트·스타일 모듈·분리된 교사 흐름 테스트.
메인이 제공한 세션·담당 반·수업 설정·학생 조회·초기화 함수를 사용한다.
서버에서 검증된 담당 반만 선택할 수 있게 하며 URL이나 화면 상태로 권한을 확대하지 않는다.
이번 수업 지정은 서버 성공 후 반영한다. 실패한 변경이나 초기화를 성공 메시지로 표시하지 않는다.
계정 초기화는 PRD의 변경 필요 상태·기존 접속 무효화·기록 보존 정책을 따른다.
학생별 개념·퀴즈·실습 진행과 제출 작품 조회를 1차 범위에 포함한다. 방문 기록을 완료율로 변환하지 않는다.
서버가 제공한 진행·제출 기록을 사용하고 학생 화면과 같은 완료 규칙을 적용한다.
승인된 조회 범위 안에서 제출 작품을 보여주며 제출본과 편집 중 초안을 혼동하지 않는다.
학생 작업 수정·임의 완료 처리 기능을 추가하지 않는다.
공통 레이아웃·서버·전역 CSS·데이터 계약 변경은 메인에 요청한다.
확인: 반 전환, 빈 반·수업 미지정, 저장 실패, 담당 밖 반 거부, 초기화 실패와 기록 보존,
  학생과 교사의 단계 진행 일치·제출 작품 조회, 좁은 화면·키보드·콘솔.
인계: 변경 파일, 구현한 흐름, 실행한 검사와 결과, 실제/모의 연결 구분, 남은 문제.
```

학생 전용 경로는 `src/components/student/`, 전용 검증은 `tests/student-ui.spec.ts`입니다. 교사 화면은 `src/app/teacher/`가 담당합니다. 현재 여러 역할을 함께 검사하는 `tests/platform.spec.ts`와 공개 홈 회귀 검사는 메인이 맡고, 두 담당자가 같은 테스트 파일을 동시에 변경하지 않습니다. 공유 작업 공간에서는 다른 담당자의 변경을 되돌리지 않습니다.

## 검증·수정 반복 규칙

`관찰 가능한 완료 조건 → 작은 구현 → 관련 검증 → 실패 원인 확인 → 수정 → 같은 조건 재검증`을 작업 단위마다 반복합니다.

- 반복마다 해결할 문제·기대 결과·검증 방법을 정합니다. 기능·화면·권한 검증을 구분하고, 미관 평가만으로 저장이나 권한의 정확성을 판정하지 않습니다.
- 실패를 고치기 위해 요구사항이나 테스트 기대값을 낮추지 않습니다. 요구사항 자체에 모순이 있으면 구현 결함과 구분해 근거를 제시합니다.
- 같은 실패가 세 번의 수정·검증에도 남으면 원인 가설·접근을 재검토합니다. 횟수가 찼다는 이유로 완료하거나 전체 작업을 자동 중단하지 않습니다. 독립적으로 진행 가능한 작업은 계속합니다.
- 정보·계정·외부 권한이 필요한 문제는 코드 수정 반복으로 해결하려 하지 않습니다. 필요한 항목과 준비된 결과를 구체적으로 설명하고 의존하지 않는 작업부터 진행합니다.
- 해당 완료 조건이 통과하면 그 작업의 반복을 끝냅니다. 새 변경이나 남은 위험이 없는 상태에서 같은 검사를 무한 반복하거나 합의 밖의 리팩터링을 추가하지 않습니다.
- 공통 코드 변경·통합 후에는 영향을 받는 흐름을 다시 검사합니다. 최종적으로 저장소의 lint·typecheck·build·E2E 및 UI 확인을 수행합니다.

## 완료 근거

| 확인할 흐름 | 통과 조건 |
| --- | --- |
| 로그인·계정 상태 | 실제 인증과 역할이 연결되고 첫 입장·초기화 후 변경을 서버에서도 요구합니다. 합의한 만료·중복 로그인·초기화 정책을 검증합니다. |
| 수업 지정·전환 | 담당 반에만 반영됩니다. 기존 열린 수업과 작업이 유지되고, 학생이 이동을 선택하며 미저장 변경은 저장 성공 후 이동합니다. |
| 저장·이어하기 | 서버에 저장한 활동·진행 상태를 재접속 후 복원합니다. 다른 계정으로 로그인했을 때 앞 사용자의 작업이 노출되지 않습니다. |
| 저장 실패·충돌 | 연결 실패를 성공으로 표시하지 않습니다. 작업을 보존하고 재시도할 수 있으며, 늦게 도착한 이전 저장이 최신 작업을 조용히 덮어쓰지 않습니다. |
| 권한 경계 | 다른 학생·담당 밖 반의 데이터 조회·수정은 화면뿐 아니라 서버와 가능한 직접 DB 경로에서도 거부됩니다. |
| 학습·제출 규칙 | 선택한 샘플에서 개념 자동 완료, 퀴즈 오답 재도전·실습 자유 이동, 검증 후 제출 성공 시 완료, 제출 후 수정본 분리를 확인합니다. 필수 활동만 기본 완료에 포함합니다. |
| 교사의 학습 확인 | 담당 반 학생의 단계별 진행과 성공적으로 저장된 제출본을 조회합니다. 학생 화면의 완료 기록과 일치하고, 재제출 전 수정 중 초안을 새 제출본으로 표시하지 않습니다. |
| 화면 사용성 | 실제 데이터의 빈 상태·처리 중·실패·성공을 구분합니다. 좁은 화면·키보드 초점·주요 조작·브라우저 콘솔을 확인하고 기존 홈을 회귀 검증합니다. |

서비스 자격 증명이나 연결이 없어 실제 검증을 못 했다면 그 부분은 미완료로 표시합니다. 에뮬레이터·모의 서비스 검증은 유용한 중간 결과이지만 실제 환경 연결 검증을 대신했다고 보고하지 않습니다. 비밀번호·학생 개인정보·API 키는 테스트 산출물과 보고에 노출하지 않습니다.

## 작업별 지시문 양식

구현을 시작할 때 확정된 범위에 맞춰 아래 항목을 채워 각 작업에 전달합니다.

```text
목표: 사용자가 할 수 있게 될 행동과 서버에 남아야 할 결과

수정 범위: 담당 파일과 공유 파일의 변경 협의 대상
입출력: 사용하는 데이터 형식·API·권한·오류 규칙
완료 조건: 성공 흐름과 반드시 막아야 하는 실패·권한 사례

인계: 변경 파일, 실행한 검사·결과, 미검증 항목, 후속 작업
```

## 연결·검증 결과와 남은 확인

검증용 수업, 에이전트 분담, 교사 화면의 범위, 단계별 퍼센트·완료 수와 전체 상태 표시는 확정했고 구현했습니다. 승인된 Firebase 대상에 서버 자격 증명을 Git 제외된 `.env.local`로 설정했고 이메일·비밀번호 및 Google 제공자 활성화, 11개 빈 반 준비와 Firestore 보안 규칙 배포를 확인했습니다. 임시 합성 계정의 실제 Auth 로그인 → 수업 지정 → 개념·퀴즈·실습 검증과 제출 → 재로그인 복원 → 교사 제출 조회, 익명 Firestore 접근 거부(403)를 통과했습니다. 시험 계정 2개·작업·요청 제한 기록을 삭제하고 시험 반의 빈 설정도 복원했습니다. 설정 절차는 [Firebase 설정 안내](FIREBASE_SETUP.md)를 따릅니다.

제공자 설정·에뮬레이터 토큰 교환 검사에 더해 실제 허용 Google 계정으로 `localhost`에서 로그인하고 교사 대시보드에 진입한 것을 사용자와 브라우저에서 확인했습니다. 담당 반 11개·빈 반·등록 학생 0명 상태를 확인했으며 호스팅 환경 검증은 후속입니다. 최종 lint·typecheck·build와 로컬 개별 검사(학생 UI 4개·API 8개·플랫폼 3개·탐색 4개·운영 1개)는 통과했습니다. 프로덕션 빌드의 `next start`와 로컬 Firebase 에뮬레이터로 실행한 CI 방식 전체 E2E 27개(홈 7·API 8·탐색 4·운영 1·플랫폼 3·학생 4)도 약 1.3분에 모두 통과했습니다. 테스트 주소를 `localhost`로 통일해 Playwright API 쿠키 전송을 확인했고 앱의 쿠키 보안 설정은 유지했습니다. 상세 근거는 HANDOFF에 기록했습니다. 실학생 등록·앱 배포·AI·EntryJS·Q&A·정식 콘텐츠는 후속 작업입니다.

반복 검증 원칙의 참고 자료: [Anthropic의 평가·개선 및 에이전트 작업 흐름 설명](https://www.anthropic.com/engineering/building-effective-agents). 세 번 재검토 규칙은 프로젝트 작업 기준이고 메인·학생·교사 분담은 사용자와 합의한 방식입니다. 해당 자료의 의무 규칙으로 해석하지 않습니다.
