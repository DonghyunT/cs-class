# 2026-11-06 저장 응답 유실 뒤 충돌 안내 검토

기준 `main`의 `f62f0d8`입니다. 코드만 읽고 판단했으며 재현하지 않았고 운영 기록도 보지 않아 발생 빈도를 모릅니다. 사용자가 수정을 미루기로 했습니다(11/6). 시작할 때 전체 E2E 실행 여부를 정합니다.

## 문제

1. 저장이 서버에 반영됐는데 응답만 끊기면(네트워크 오류, 65초 시간 초과) 화면의 `server.current`는 옛 `revision`에 머뭅니다.
2. 내용을 그대로 다시 저장하면 서버가 같은 내용으로 보고 그대로 돌려줍니다(`tests/classroom-api.spec.ts`의 응답 유실 재시도).
3. 더 고친 뒤 저장하면 옛 `revision`을 보내 `src/lib/server/classroom.ts`의 `mutateWork`가 `REVISION_CONFLICT`로 거절하고, 다른 탭을 쓴 적이 없어도 "다른 탭" 안내가 뜹니다.
4. `src/components/student/lesson-editor.tsx`의 비교 화면에서 `현재 입력을 새 버전으로 저장`을 누르면 잃는 것이 없고, `서버 기록으로 이어하기`를 누르면 끊긴 저장 이후의 입력이 사라집니다.

저장 중에도 `useWork`의 `update`는 입력을 받으므로 응답을 기다리는 동안 학생이 계속 고칠 수 있습니다. #107의 65초 제한으로 이 상황에 들어가는 길이 하나 늘었습니다.

## 판단

급하지 않습니다. 응답 유실, 이후 수정, `서버 기록으로 이어하기` 선택이 겹쳐야 입력을 잃고, 잃는 범위는 끊긴 저장 이후의 입력입니다. 다만 안내가 틀렸고 비교 화면은 블록 개수 위주로 보여 주어 학생이 차이를 알아보기 어렵습니다.

## 수정안

`src/components/student/use-work.ts`의 `flush`만 고칩니다. 서버와 데이터 구조는 바꾸지 않고, 자동 저장·자동 재전송을 추가하지 않습니다(추정 15~20줄과 테스트 1개).

1. 결과를 알 수 없는 저장 실패(4xx가 아닌 실패)면 보낸 내용을 화면 메모리에 기억합니다.
2. 학생이 다시 저장하면 보내기 전에 `classroomApi.work`로 서버 기록을 한 번 읽습니다.
3. 읽은 결과에 따라 처리합니다.
   - 끊긴 저장과 내용이 같음: 그 기록을 이어받아 새 `revision`으로 저장합니다.
   - 그대로임: 평소처럼 저장합니다.
   - 다른 내용으로 바뀜: 지금의 비교 화면을 보여 줍니다.
   - 읽기 실패: 입력을 유지하고 오류를 그대로 둡니다.
