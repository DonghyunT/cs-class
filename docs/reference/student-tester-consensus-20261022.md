## 0. 전체 결론

**학생이 즐거워한 것은 직접 해 보고 결과가 바로 보이는 순간이었고, 가장 오래 막힌 곳은 엔트리 블록 조립과 '왜 틀렸는지 모르는' 피드백이었습니다.** 문구·그림 정리보다 먼저, 학생의 활동을 막는 실습 결함과 피드백을 고쳐야 모든 수업의 경험이 좋아집니다.

- 화면 체험에서 학생을 막은 결함 4개를 코드나 재현으로 확인했습니다.
  - 반복 수업에서 그린 정사각형이 실행 직후 사라집니다.
  - 기초 미션 1의 힌트와 검증 기준이 서로 다릅니다.
  - 작업실이 1024px 화면에서 잘립니다.
  - 제출 뒤 다시 들어오면 실행 확인이 0/2로 돌아갑니다.
- 피드백 문제는 여섯 수업 모두에 있습니다. 오답 학생은 미리 보이던 힌트를 다시 받거나, 복습 수업처럼 모든 문항에서 같은 문장을 받습니다. 개념 확인과 퀴즈 모두 찍어서 통과할 수 있습니다.
- 조건 수업 개념 흐름(§4)의 방향은 유지합니다. 다만 [HANDOFF](../HANDOFF.md) 다음 작업 5번에 따라 실제 수업 관찰 뒤에 정합니다.
- 모든 수업에 적용할 원칙과 우선순위는 [§13](#13-모든-수업을-위한-원칙과-우선순위)에 모았습니다. 사용자가 정해야 할 항목도 그곳에 있습니다.

## 1. 결론(조건 수업 개념 흐름)

**기존 다섯 개념의 순서와 10월 21일의 화면 방향을 유지하고, 같은 자유투 기록에 서로 다른 질문을 던지는 흐름으로 다듬습니다.** 같은 배경을 쓰는 것과 하나의 작품을 계속 확장하는 것은 구별합니다.

사회자의 최초 제안 중 ‘평균 판정을 마지막 중첩 선택까지 연결한다’는 부분은 철회했습니다. 현재 자유투 미션은 성공 개수를 한 번 입력받는 독립 작품입니다. 이를 평균 판정으로 설명하면 본문·그림·실습·채점이 달라집니다.

3라운드 후 민서·도윤·서연 모두 최종안 V3에 **동의**, 남은 설계 차단 조건 **없음**으로 답했습니다. 이는 가상 페르소나의 설계 수용이며 실제 학생의 만족·학습 효과나 구현 완료를 뜻하지 않습니다.

같은 날 코드와 대조한 후속 검토에서 보완점이 나왔습니다. 개념 확인의 오답 풀이는 답을 베끼게 할 수 있고, 실제 변경 범위는 문구·그림 정리보다 큽니다. 저장된 옛 문구도 남고, 공통 원칙은 다른 수업에 아직 이어지지 않습니다. 구현 전에 [§11](#11-후속-검토-코드-대조-보완)을 함께 봅니다.

## 2. 패널과 검토 방법

사용자 요청에 따라 서브에이전트 3명을 독립 호출했습니다. IQ 160은 높은 추론 능력을 가정한 역할 설정이며 검사 결과가 아닙니다. 높은 추론 능력이 프로그래밍 선행지식·블록 조작 경험·지속적인 주의를 대신한다고 가정하지 않았습니다.

| 가상 학생 | 배경과 성향 | 검토의 초점 |
| --- | --- | --- |
| 민서 | 중2, 신중한 독해형, 프로그래밍·엔트리 조립 경험 없음 | 설명은 이해하지만 블록을 어디에 넣는지 모르는 순간, 오답 후 재시도 |
| 도윤 | 중3, 엔트리 경험 있음, 실험·반례·자율성 중시 | 과잉 안내와 답 베끼기, 경계값, 다른 상황에 적용하기 |
| 서연 | 중2~중3, 빠르게 훑는 성향, 엔트리 경험 적음 | 값·용어·질문 대상의 변경, 저장·검증·제출 상태 구별 |

각자 관련 코드와 화면 기준을 읽고 독립 의견을 냈습니다. 사회자가 다른 학생의 주장과 반론을 전달하고 수정안을 재검토시켰습니다. 마지막에는 동일한 V3를 보내 동의·조건부 동의·반대와 남은 차단 조건을 명시하도록 했습니다. 의견 수렴을 위해 동의하도록 요구하지 않았습니다.

패널은 파일만 검토했습니다. 브라우저 조작·실제 블록 조립·학생 관찰·운영 접속·앱 테스트는 수행하지 않았습니다.

## 4. 최종 합의: 다섯 개념의 흐름

공통 배경은 **“자유투를 10개씩 두 차례 연습했어요. 첫 기록 A는 6개, 두 번째 기록 B는 4개예요.”**입니다. ‘두 번 던져 6개 성공’처럼 단위가 맞지 않는 표현은 쓰지 않습니다.

처음에 “같은 자유투 기록으로 계산·판단·실행을 차례로 배워요. 실습 작품은 각각 만들어요.”라고 짧게 안내합니다. 매 화면에 독립 작품 경고를 반복하지 않고, 질문이 바뀌는 곳만 짚습니다.

| 개념 | 예시와 학생에게 보여 줄 연결 문장 | 다음 개념을 예상하는 질문 |
| --- | --- | --- |
| cc0 산술 연산자 | “두 차례 기록의 평균을 계산해요. (6+4)÷2=5예요.” 괄호 안 계산→나눗셈을 보여 줍니다. | “계산뿐 아니라 기록이 목표를 달성했는지도 판단할 수 있을까요?” |
| cc1 비교 연산자 | “이번에는 평균이 아니라 첫 번째 기록 A를 봐요. 목표는 5개 이상이에요.” 6≥5는 참, 6<5는 거짓입니다. | “두 번째 기록 B도 함께 판단하려면 어떻게 할까요?” |
| cc2 논리 연산자 | “A와 B가 각각 5 이상인지 판단해요.” (A≥5)는 참, (B≥5)는 거짓이므로 AND는 거짓, OR는 참입니다. NOT은 우선 NOT(A≥5)만 다룹니다. | “이 판단 결과에 따라 실행할 말을 고를 수 있을까요?” |
| cc3 제어 구조 | “첫 번째 기록 A로 돌아와, 판단에 따라 실행할 말을 골라요.” A≥5이면 ‘목표 달성’, 아니면 ‘다음에 도전’입니다. 순차·선택·반복의 기존 그림을 유지하고 이번 중심은 선택이라고 설명합니다. | “이 선택 구조를 엔트리 블록으로 어떻게 만들까요?” |
| cc4 만일 ~ 아니면 블록 | “새 예시 작품에서는 성공 개수를 한 번 물어요. 입력한 값은 ‘대답’에 들어가요.” 대답≥8, 아니면 대답≥5, 아니면의 세 경우를 다룹니다. 앞의 A·B·평균이 자동으로 이어지는 작품으로 설명하지 않습니다. | “6을 직접 입력하면 어느 가지를 지나갈까요? 5와 8에서는 어떨까요?” |

‘5 이상’을 ‘5를 넘으면’이라고 설명하지 않습니다. 같음을 포함하는 기준을 말과 식에서 맞춥니다.

### 그림과 보조 사례

- 10월 21일의 짧은 핵심 제목, AND·OR·NOT 병기, 참·거짓 화살표, 엔트리가 그린 중첩 선택 그림을 유지합니다.
- cc1의 기존 75·60 그림은 A=6·목표 5와 맞춥니다. 그림의 접근성 설명도 같은 값으로 바꿉니다.
- cc2는 조건→참·거짓→결합 결과가 연결되어야 합니다. 산술 덧셈 기호처럼 읽히는 그림 표기는 실제 조건 결합임이 드러나는지 확인합니다.
- cc4는 기존 ‘대답’ 기준의 캡처와 새 본문이 일치하므로 무조건 다시 만들지 않습니다. 블록 문구나 조건을 바꿀 때만 실제 엔트리 렌더링으로 다시 캡처합니다.
- 기본 6·4 외에 5·5와 4·4를 보조 예시나 확인 장면에 분산합니다. OR는 둘 다 참이어도 참이라는 점과 같음의 경계를 확인합니다. 한 화면에 긴 진리표와 해설을 모두 펼치지 않습니다.
- NOT의 첫 설명에서 부정하는 범위를 괄호로 표시합니다. NOT(A≥5)는 A<5입니다. ‘둘 다 아니다’ 같은 모호한 확장은 이번 필수 흐름에 넣지 않습니다.
- 시험·놀이기구·방탈출 등 다른 상황의 기존 퀴즈와 미션은 유지합니다. 개념의 연결과 배운 판단을 다른 상황에 적용하는 확인은 서로 다른 역할입니다.

## 5. 최종 합의: 퀴즈 설명

현재 기초·조건·반복 퀴즈는 정답이면 explanation, 오답이면 hint를 반환합니다. 정답을 선택한 학생보다 오답을 선택한 학생에게 풀이가 적다는 문제가 있습니다. 개념 확인도 정답일 때 해당 문항 풀이 대신 개념 설명을 반환하는 구조입니다.

합의한 방향은 다음과 같습니다.

1. 답하기 전에는 기존 힌트를 유지합니다.
2. 채점 후에는 정오답 모두 같은 수준의 근거를 제공합니다. 오답 표시는 분명하게 유지합니다. 이 항목은 퀴즈에만 적용합니다. 개념 확인 문항은 [§11.1](#111-개념-확인의-답-베끼기-위험)을 따릅니다.
3. 풀이는 2~4개의 짧은 문장으로 값 넣기→계산 또는 참·거짓→실행 경로→결과 중 필요한 단계만 설명합니다. 개념 정의 전체를 반복하지 않습니다.
4. 기존 결과 메시지 공간을 우선 활용합니다. 별도 풀이 화면·접기 버튼·이유 입력창·통과 관문을 만들지 않습니다.
5. 같은 문항의 재도전은 풀이를 읽고 판단을 다시 구성하는 활동입니다. 정답을 기억해 재선택한 결과만으로 독립 이해를 입증했다고 보고하지 않습니다.

자유투 6개 문항의 예시 풀이:

> 6≥8은 거짓이므로 첫 번째 말하기는 실행하지 않아요. ‘아니면’ 안에서 6≥5를 확인하면 참이므로 ‘잘했어요!’를 말해요. 마지막 ‘아니면’은 실행하지 않아요.

8개에서는 첫 조건이 참이므로 5개 조건까지 내려가지 않는다는 설명도 필요합니다. ‘5 이상’을 먼저 확인하면 8도 그 가지에 들어간다는 반례를 짧게 보여 줄 수 있습니다.

개념 확인 문항은 정의 반복보다 그 문항에서 계산·판단한 이유를 우선 설명합니다. 기존 서버의 메시지 경로에서 가능한 최소 변경을 검토하되, 퀴즈와 개념 확인의 전달 경로를 혼동하지 않습니다.

## 6. 최종 합의: 실습 조립 안내

목표는 언제나 짧게 보이게 하고 바로 제작을 시작할 수 있게 합니다. 자세한 번호 안내는 기존 접힌 ‘블록 연결 힌트’ 안에 둡니다. 안내에는 필요한 블록의 실제 이름, 목적, 저장 시점, 들어갈 슬롯을 포함하되 완성 프로젝트를 복사하게 만들지 않습니다.

| 미션 | 최소한 보충할 정보 | 만든 뒤 확인할 사례 |
| --- | --- | --- |
| 곱셈·평균 | 각 질문 직후 대답을 A/B에 저장하는 이유와 시점. 평균은 나눗셈 왼쪽 칸에 덧셈을 넣고 그 두 칸에 A/B를 넣으며 계산 결과를 말하기 칸에 넣는 위치 | 서로 다른 두 쌍의 입력으로 결과가 바뀌는지 확인. 두 입력값과 결과를 구분 |
| 합격/불합격 | 질문 다음에 ‘아니면’이 있는 만일 블록 연결, 조건 칸과 참·거짓 쪽 말하기 위치 | 점수 59·60, 같음이 포함되는 이유 |
| 자유투 평가 | 한 번 묻는 성공 개수 작품임을 명시. 범위는 8 이상 / 5 이상 8 미만 / 5 미만. 두 번째 만일을 첫 번째 아니면 안에 넣는 위치 | 성공 개수 4·5·7·8을 직접 입력. 평균의 결과나 평균 미션의 입력쌍과 혼용하지 않음 |
| 방탈출 | 각 응답의 A/B 저장, A=1과 B=1을 또는 양쪽 칸에 넣은 뒤 완성한 판단을 만일의 조건 칸에 넣는 순서 | 1·0, 0·1, 0·0. 여력이 있으면 1·1도 예측 |
| 정사각형·정다각형 | 그리기 시작, 반복 안에 들어갈 이동·회전, 횟수와 회전각 슬롯. 전체 과정을 시작할 때의 위치·방향 등 필요한 준비를 실제 시작 작품과 대조 | 정사각형 뒤 변의 수 3·5·6으로 변형 |

평균 hint는 기존 키 검증용 fixture와 연결되어 있으므로 고정 문구를 바꾸거나 fixture를 다시 만들어 통과시키지 않습니다. 기존 힌트를 보존하면서 번호 안내를 제공하는 가장 작은 위치·구조는 구현 때 정합니다.

패널은 번호 안내의 단계 수보다 ‘다음 질문을 하면 대답이 바뀌므로 A에 저장한다’ 같은 이유가 포함되는 것을 중시했습니다. 이유를 학생에게 다시 입력하게 하는 기능은 필요하지 않습니다.

## 7. 최종 합의: 화면 전반의 일관성

- 같은 행동의 버튼은 같은 용어를 씁니다. 예: 힌트 보기, 먼저 실습하기. 저장·실행·정답 확인·조건 검증·작품 제출처럼 역할이 다른 행동까지 하나의 말로 합치지 않습니다.
- 조건·반복의 정적 그림에 ‘직접 바꾸고’라고 안내하지 않습니다. ‘예시를 읽고 결과를 예상해 보세요’처럼 실제로 할 수 있는 행동을 안내합니다. 기초 수업의 조작 체험은 유지합니다.
- 현재 ‘먼저 해볼 작은 실험’의 상당수는 작품이 있어야 가능합니다. 조립 안내 뒤 ‘만든 뒤 확인하기’로 순서를 맞춥니다.
- 조건·반복 퀴즈의 ‘강아지’는 현재 시작 오브젝트와 맞지 않습니다. ‘어떤 말이 나올까요?’처럼 선택한 오브젝트와 무관한 표현을 씁니다.
- 현재 작업실에는 저장·검증·제출 구분과 ‘이전 제출 유지 · 수정 중’ 표시가 이미 있습니다. 새 상태 체계를 만들지 않습니다.
- 미션 목록은 제출본 존재만으로 ‘제출 완료’를 표시하므로, ‘제출한 기록 있음’처럼 과거 기록을 뜻하는 말로 현재 작품의 상태와 구별합니다. 교사 미리보기의 체험 문구도 해당 의미를 유지합니다.
- 집중 모드를 나왔다고 학생이 접어 둔 안내 상태가 그대로 보존된다고 설명하지 않습니다. 현재 동작과 다른 약속을 추가하지 않습니다.
- 기초의 조작 체험, 조건·반복의 정적 그림, 복습의 활동 차이는 학습 목적에 따른 차이로 유지합니다. 모든 화면의 모양을 획일화하지 않습니다.

## 8. 범위와 구현 확인 기준

이번 합의는 학습 흐름·문구·그림의 내용 일치와 도움 설명에 집중합니다. 새 통합 미션, 새 필수 문항, 라이브러리, 진리표 조작 기능, 자동 조립, 새로운 저장 항목·채점 기준·데이터 초기화는 포함하지 않습니다.

기존 개념·문항·미션 ID와 완료 기록은 보존합니다. 보조 예시 추가 때문에 기존 답의 의미가 바뀌지 않아야 합니다. 기존 확인 문항의 질문·정답 의미까지 바꿔야 한다면 완료 기록에 미칠 영향을 별도로 판단해야 하며, 이번 합의가 그 변경을 자동 승인하는 것은 아닙니다.

아래는 아직 실행하지 않은 구현 확인 기준입니다. 가상 학생이 실제로 수행한 결과가 아닙니다.

| 기준 | 확인할 내용 |
| --- | --- |
| 흐름 | 각 화면 첫 두 문장에서 현재 판단 대상이 평균·A·A/B·새 대답 중 무엇인지 알 수 있음 |
| 논리 | 6·4, 5·5, 4·4에서 AND/OR와 NOT(A≥5)의 결과를 설명할 수 있음. 5·5에서 OR도 참임 |
| 중첩 | 자유투 4·5·7·8에서 기대한 말이 나오며, 8은 첫 갈래에서 끝남 |
| 조립 | 안내를 열어 입력 보관과 계산/조건 슬롯을 조립할 수 있고, 첫 대답을 저장하는 이유를 설명할 수 있음 |
| 자율성 | 안내를 열지 않아도 목표를 알고 시작할 수 있고, 상세 안내를 강제로 거치지 않음 |
| 풀이 | 퀴즈는 정답과 오답 모두 채점 후 풀이가 보이고 오답 판정은 유지됨. 개념 확인은 오답 때 답을 드러내지 않음(§11.1). 실제 식·그림·입력·풀이가 일치함 |
| 전이 | 다른 상황의 기존 퀴즈에서도 판단 근거를 설명할 수 있음. 같은 문제 재도전만으로 대체하지 않음 |
| 상태 | 제출 후 수정한 경우 과거 제출 기록과 현재 작품 상태를 구별할 수 있음 |
| 화면 | 데스크톱·좁은 화면에서 도움·풀이가 조립 공간을 과도하게 밀지 않고 키보드로 접근 가능하며 콘솔 오류가 없음 |

구현 시에는 관련 단위·서버 채점 검사와 조건·반복·기초·교사 미리보기의 변경 영향에 맞는 선별 E2E, 실제 브라우저 조작으로 확인합니다. 기존 화면 일관성 검사의 수업 목록이 조건·반복까지 포함하는지도 확인해야 합니다. 전체 E2E 실행·push·배포에 관한 승인은 이 보고서의 합의에 포함되지 않습니다.

## 11. 후속 검토: 코드 대조 보완

2026-10-22에 사용자 요청으로 서브에이전트 2명이 이 보고서를 같은 기준 커밋(`870fe4c`)의 코드와 대조했습니다. 한 명은 보고서가 쓴 사실을 파일·줄 단위로 확인했고, 다른 한 명은 교육적 타당성과 모든 수업으로의 일반화를 검토했습니다. 핵심 줄은 사회자가 다시 열어 확인했습니다.

보고서가 현재 코드에 대해 쓴 사실 중 틀린 것은 없었습니다. 아래는 빠졌거나 조정이 필요한 점입니다. 이 절도 구현 계획이나 현재 동작 기준이 아닙니다.

### 11.1 개념 확인의 답 베끼기 위험

§5의 '정오답 모두 풀이'를 개념 확인 문항에 그대로 적용하면 위험합니다(심각도 높음).

- 개념 확인은 보기가 2~3개입니다. 정답을 맞히기 전까지 '정답 확인' 버튼이 계속 보여 바로 다시 누를 수 있습니다([공통 개념 화면](../../src/components/student/lesson-concept-panel.tsx), [채점 처리](../../src/lib/server/learning.ts)).
- 오답 뒤에 정답 근거를 보여 주면 다음 시도는 확인이 아니라 베끼기가 됩니다. 필수 문항을 정답으로 해결해야 완료라는 [PRD](../PRD.md) §3.1 기준의 의미도 약해집니다.
- 퀴즈는 상대적으로 덜 위험하다고 봤습니다. '틀린 문제 다시 풀기'를 시작하면 서버가 그 문항의 답과 이전 피드백을 지우고, 감점 없는 형성평가이기 때문입니다. 그러나 화면 체험에서 이 판단은 반박되었습니다(§12.4).
- 복습 수업으로 넓히면 더 위험합니다. 복습 퀴즈 풀이는 "정답은 ②번입니다!"처럼 답 번호로 시작합니다([복습 퀴즈 풀이](../../src/lib/server/review-quiz.mjs)).

조정안:

| 활동 | 정답일 때 | 오답일 때 |
| --- | --- | --- |
| 퀴즈 | 그 문항의 짧은 풀이 | 같은 수준의 풀이(§5 유지) |
| 개념 확인 | 개념 본문 반복 대신 그 문항의 풀이 | 미리 보이는 힌트보다 한 단계 구체적으로 되묻기. 답은 드러내지 않음 |

### 11.2 실제 변경 범위

보고서는 '새 기능 없이 문구·그림 정리'라고 했지만, 항목마다 범위가 다릅니다.

| 항목 | 실제로 바뀌는 곳 | 크기 |

그 밖의 사실 보정:

- §6 표의 '곱셈·평균'은 서로 다른 수업의 미션입니다. 곱셈은 기초 수업, 평균은 조건 수업입니다.
- 방탈출과 비밀번호 금고는 필수가 아닌 선택 도전 미션입니다.
- 곱셈 힌트에는 이미 'B를 물으면 대답이 바뀐다'는 저장 이유가 있습니다. 평균 힌트에는 없습니다.
- cc0은 이미 A=6, B=4의 평균을 씁니다. 새 흐름은 이 값을 cc1~cc3까지 넓히는 일입니다.
- cc4 캡처는 '대답' 기준이지만 묻기 블록은 없습니다. 새 본문 "성공 개수를 한 번 물어요"와 그림이 완전히 같지는 않습니다.
- 자유투 미션의 현재 실험 안내는 9·7·4라서 경계값 5와 8이 빠져 있습니다.
- 화면 일관성 검사는 기초·복습 수업만 대상으로 하고, 조건·반복 수업은 실제로 빠져 있습니다([화면 일관성 검사](../../tests/lesson-ui-consistency.spec.ts)).
- 40분 수업 시간 예산을 따지지 않았습니다. 개념 단계는 10분에 5개인데, 보조 사례·풀이·조립 안내가 모두 읽을 양을 늘립니다.
- 이 개념 흐름은 [HANDOFF](../HANDOFF.md) 다음 작업 5번에서 "수업에서 반응을 보고 정합니다"로 보류된 항목입니다. 가상 패널 결과는 그 관찰을 대신하지 않습니다.

### 11.3 저장된 옛 문구와 답 번호

§8의 'ID·완료 기록 보존'만으로는 막을 수 없는 위험이 있습니다.

- **옛 문구가 계속 보임(코드로 확인):** 채점 메시지는 채점한 순간의 문장 그대로 학생 기록의 `quizFeedback`·`conceptFeedback`에 저장됩니다. 이미 채점받은 학생에게는 문구를 바꾼 뒤에도 옛 문구가 보입니다. 개념 확인을 이미 완료한 학생은 답 선택이 잠겨 새 문항이나 새 풀이를 다시 보지 않습니다.
- **완료 기록은 유지됨(코드로 확인):** 완료는 해결한 문항 ID 목록과 제출본 유무로만 계산합니다. 문구만 바꾸면 완료 표시는 바뀌지 않습니다.
- **답 번호 어긋남(추론, 재현하지 않음):** 저장된 답은 선택지 번호이고, 서버는 저장할 때마다 그 번호가 현재 문항에 있는지 검사합니다. 선택지를 줄이면 옛 번호가 남은 학생의 저장이 `INVALID_ANSWER`로 거절될 수 있습니다. 순서만 바꿔도 화면에 다른 답을 고른 것처럼 보일 수 있습니다. 저장된 옛 답을 정리하는 코드는 찾지 못했습니다.

따라서 기존 문항의 선택지 수·순서는 바꾸지 않습니다. 바꿔야 한다면 기존 학생 기록의 처리 방법을 구현 전에 사용자와 정합니다.

### 11.4 공통 원칙과 권장 순서

이 절에 있던 공통 원칙 표와 권장 순서는 화면 체험 결과와 합쳐 [§13](#13-모든-수업을-위한-원칙과-우선순위)으로 옮겼습니다.

이 보고서 방법론(§2)의 추가 한계:

- 세 학생이 같은 모델이라 의견이 서로 비슷해지기 쉽습니다.
- 사회자가 반론을 전달하는 방식이 결론을 한쪽으로 끌 수 있습니다.
- 세 명 모두 추론 능력이 높은 설정이라 읽기가 느린 학생, 의욕이 낮은 학생의 시각은 없습니다.
- 그래서 만장일치는 약한 근거입니다. 코드로 확인된 문구·그림 어긋남은 믿을 만하지만, 학습 효과·지루함·이해도 판단은 가설로 봅니다.

참고(범위 밖, 확인하지 않음): 정답 번호(`correct`)가 든 [기초 개념·퀴즈 데이터](../../src/lib/classroom/programming-data.ts)를 브라우저에서 실행되는 화면 코드가 불러옵니다. 빌드 결과물에 정답이 들어가 학생이 개발자 도구로 볼 수 있는지는 확인하지 않았습니다.

후속 검토에서 실행한 것은 파일 읽기, grep, git 조회입니다. 앱 테스트 실행은 0개이고 앱·브라우저·빌드는 실행하지 않았습니다. 선택지 변경 시 저장 거절과 정답의 브라우저 노출은 재현하지 않았습니다.

### 12.2 학생들이 즐거워한 것(지켜야 할 것)

- **직접 조작하면 결과가 바로 바뀌는 개념 체험:** 기초 개념 2~5(블록·텍스트 전환, 이름 넣고 인사말 만들기, A에 3 저장), 복습의 빵 잼 바르기·물 붓기 반복·순서도 경로 따라가기입니다. 하린과 태민이 가장 즐거웠던 순간으로 꼽았습니다.

### 12.4 이전 판단과 달라진 점

1. **퀴즈도 찍기 위험이 있습니다(§11.1 수정).** 같은 문항을 다시 풀게 하므로 3지선다 퀴즈는 두세 번 찍으면 완료됩니다. 답하기 전 힌트가 규칙을 그대로 말하는 문항도 있습니다.
2. **블록 조립의 조작 부담이 문구 문제보다 큽니다.** 패널(§2)은 파일만 봐서 이 부분을 볼 수 없었습니다. 하린·준호·예린은 체험 시간의 대부분을 블록 찾기와 끼우기에 썼습니다.
3. **지금 더 큰 문제는 오답 학생이 이유를 받지 못하는 것입니다.** §11.1의 '답 베끼기'는 오답 피드백을 바꿀 때 함께 막을 위험입니다. 오답 피드백 개선을 먼저 하되, 답을 드러내지 않는 기준을 지킵니다.
4. **미션 목록의 '제출 완료' 문구(§7)는 우선순위가 낮습니다.** 제출 시각 배너가 있어 혼동이 작았습니다. 대신 재진입 뒤 '0/2'가 실제로 불안을 만들었습니다.
5. **§8 확인 기준에 빠진 것:** 1024px 화면에서 작업실 전체가 보이는지, 그리기 결과가 무대에 남는지, 힌트대로 만든 작품이 검증을 통과하는지입니다.

## 13. 모든 수업을 위한 원칙과 우선순위
