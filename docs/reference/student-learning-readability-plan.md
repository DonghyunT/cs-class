## 1. 사용자 선택과 작업 경계

- 운영 수업 `programming-13`·`review-sandwich`·`review-abstraction`·`review-flowchart`의 개념·퀴즈·실습을 개선합니다.
- 파랑을 주요 조작·선택·초점에 유지하고, 살구·주황 한 계열을 보조색으로 사용합니다.
- 개념과 퀴즈는 한 번에 하나씩 크게 표시하며 목록·번호로 자유롭게 이동합니다.
- 10/6 추가 휴먼 리뷰에 따라 실습은 기본 폭으로 엽니다. ‘작업실 넓게 보기’를 눌렀을 때 좌측 탐색을 접고 확장합니다. 학생이 수동으로 선택한 폭은 같은 수업 화면을 열어둔 동안 존중합니다.
- 학생 주 사용 환경은 **데스크톱 PC**입니다. 1440×900·1920×1080을 주 검토 화면, 1280×720을 낮은 창 검토 화면으로 정합니다. 모바일·키보드 접근도 유지합니다.
- 사이트의 색상 리듬을 위해 홈·학생 대시보드·열린 수업의 기존 안내·예시·그래픽에도 같은 보조색을 소량 적용합니다. 대시보드·로그인·교사 화면의 탐색 구조를 다시 설계하지 않습니다.
- 과거 검증 수업 3종에는 공통 스타일·실습 폭의 호환성을 유지하되 새로운 개념 체험을 추가하지 않습니다. 폭 전환 버튼이 없는 순서 배열 수업 2종은 기존 기본 폭을 유지하고, 기존 EntryJS 검증 수업은 편집기의 폭 정책을 함께 적용합니다. 공개 프로그래밍 프로토타입은 공유 부품의 변경 영향을 확인합니다.

### Global Constraints

- 기존 단일 저장 흐름과 저장 실패·충돌·입력 확정·이동 보호·이전 제출본 보존을 유지합니다.
- 개념·퀴즈 완료로 다음 단계 진입을 잠그거나 정답 뒤 자동으로 화면을 넘기지 않습니다.
- 새 UI·상태 관리·모션 패키지, 체험용 AI 호출, 자동 음성, 새 통계 수집을 추가하지 않습니다.
- 화면별 스타일은 담당 컴포넌트 옆 CSS Module에 둡니다. 전역 CSS에는 공통 색상 토큰만 추가합니다.
- 검사는 `demo-cs-class`와 로컬 Auth9099·Firestore8080·`http://localhost:3000`만 사용합니다. 처음 계획의 운영 배포는 별도 범위였으며, 이번 재개에서 선생님이 최종 검증 후 기존 Production 배포·인계를 승인했습니다. 운영에 테스트 시드·합성 계정을 추가하지 않습니다.

실습 재료·순서도 기호·핵심/노이즈의 의미 있는 기존 색과 교사 로그인 색을 유지합니다. 보조색을 모든 버튼·카드에 분산하지 않습니다. 경고·오류·재도전은 제목과 아이콘으로도 구분하며 색만으로 판단하게 하지 않습니다. 기존 `accent`·`secondary` 버튼 토큰을 일괄 주황으로 바꾸지 않습니다.

- 학습 본문은 데스크톱 18px·모바일 16px, 핵심 조작 라벨은 16px, 보조 정보는 최소 14px로 정합니다. 본문 행간은 1.7, 주요 제목은 24~28px를 사용합니다.
- 조작 영역은 최소 44×44px를 확보합니다. SVG 전체를 확대해도 작은 내부 라벨이 남으면 DOM 설명을 함께 제공하거나 라벨 배치를 고칩니다.
- 개념은 읽기 폭을 유지하면서 큰 체험에 가용 폭을 배분합니다. 설명은 약 30~42자 너비로 제한합니다. 목록은 상단의 줄바꿈 가능한 버튼 그룹으로 두어 본문 폭을 잠식하지 않게 합니다.
- 퀴즈는 최대 880px 중앙 단일 문항 영역을 사용합니다. 긴 문항·선택지는 높이가 자연스럽게 늘어나게 합니다.
- 학생이 넓게 보기를 선택한 실습은 본문의 최대 폭 제한을 해제하고 좌우 여백을 데스크톱 16px·820px 이하 12px로 줄입니다. 초점 테두리·스크롤바와 조작 영역이 잘리지 않게 합니다.
- 실습에서는 제목·안내를 간결하게 정리하고 상세 진행은 기존 펼치기에 둡니다. 대시보드 이동·저장 상태·단계 선택·저장 오류는 쉽게 찾을 수 있게 유지합니다.

## 3. 개념: 관찰할 지점이 있는 큰 체험

한 개념의 순서는 **개념 목록 → 제목과 목표 → 관찰 질문 → 체험과 조작 → 가까운 결과 설명·핵심 정리 → 기존 확인 문제 → 이전/다음**입니다. 관찰 질문은 추가 필수 답변·채점 단계가 아닙니다. 처음에는 예시의 시작 상태를 보여주고 학생이 값을 바꾸거나 비교 명령을 선택해 실행합니다.

- 동시에 큰 체험 하나를 중심에 둡니다. 같은 개념에 두 예시가 필요한 경우 예시 선택기로 전환합니다. 작은 체험 카드 여러 개를 나란히 늘리지 않습니다.
- 입력·처리·출력, 변경 전·후, 조건과 실행 경로를 가까이 배치합니다. 바뀐 부분은 색과 라벨·선·횟수 등으로 함께 표시합니다.
- 모든 체험에 재시도 또는 초기화 방법이 있습니다. 실행 장면에는 중지·한 단계 실행을 제공하고, 움직임 줄이기에서는 단계별 결과를 바로 보여줍니다. 학생 입력 없이 지속 재생하거나 빠르게 점멸하지 않습니다.
- 정답 뒤에는 이유를 읽을 수 있고, 오답 뒤에는 다시 볼 관찰 지점과 `체험 다시 보기`를 제공합니다. 정답 여부를 판단하는 기존 서버 피드백은 보존합니다.
- 완료 개념도 체험을 다시 사용할 수 있습니다. 버튼을 누르거나 그림을 본 것만으로 개념 완료를 만들지 않습니다.

### 학습 위치와 체험 상태

- 같은 수업에서 단계만 왕복하면 활성 개념·문항과 선택 답안을 유지합니다. 선택 위치는 `WorkEditor`에 올려 패널이 교체돼도 잃지 않게 합니다.
- 새로고침·다른 수업에서 재진입하면 서버에 저장된 단계를 복원합니다. 개념은 **첫 미완료 ID**, 모두 완료했으면 첫 개념을 보여줍니다. 완료 개수를 개념 위치로 추정하지 않습니다.
- 개념 체험값·실행 장면은 일시적인 UI 상태입니다. 재진입 시 시작 상태로 돌아갈 수 있음을 짧게 안내하며, 저장되는 답안·완료 기록·실습 작품과 혼동하지 않게 합니다. 이번에는 체험값·현재 개념/문항 번호의 서버 저장을 추가하지 않습니다.

## 4. 퀴즈: 한 문제씩 풀되 길을 잃지 않기

- 문항 번호·현재 위치·전체 해결 수를 표시합니다. 번호 선택·이전/다음으로 자유롭게 이동하며 답을 선택했다고 자동 이동하지 않습니다.
- 번호에는 미답변/답변 표시를 하고, 채점 후에는 해결/재도전 표시를 추가합니다. 현재 위치는 별도의 선택 형태로 구분합니다. 미답변을 오답처럼 표현하지 않습니다.
- 회차의 모든 답을 선택한 뒤 기존처럼 회차 전체를 채점합니다. 미답변이 남으면 `답하지 않은 문제로 이동`을 제공해 첫 미답변 문항으로 보냅니다.
- 채점 직후 전체 해결 수와 이번 회차의 재도전 문항 바로가기를 보여줍니다. 기존 문항별 해설·힌트·`틀린 문제만 다시 풀기`를 유지합니다. 맞힌 기록은 재도전 대상에서 제외합니다.
- 재진입 초기 문항은 채점 전 첫 미답변, 채점 후 첫 오답으로 정합니다. 해당 문항이 없으면 회차의 첫 문항을 보여줍니다. 재도전 새 회차는 첫 재도전 문항을 보여줍니다.
- 진행률의 분모는 전체 문항 수를 유지합니다. 퀴즈 진행 중 실습으로 이동할 수 있으며 이동 전 저장 확인을 유지합니다.
- 보기 스타일을 정답 여부에 따라 미리 다르게 하지 않습니다. 힌트는 기본으로 접고 필요한 경우 학생이 엽니다. 서버가 판정한 해설에 오답을 점수처럼 과장하는 장식을 더하지 않습니다.

## 5. 실습: 작업 공간과 입력·결과의 거리

### 폭과 초점

- `Classroom`이 현재 학습 단계와 수동 폭 선택을 분리해 관리합니다. 실습의 수동 선택 초기값은 기본 폭이고, 개념·퀴즈는 읽기 배치로 돌아갑니다.
- 같은 사용자·수업의 화면을 열어둔 동안 수동 폭 선택을 기억합니다. 미션 이동·화면 크기 변경·개념 왕복으로 초기화하지 않습니다. 새로고침·다른 수업 진입에서는 실습 기본값을 다시 적용합니다.
- 폭 전환은 CSS로 처리합니다. iframe의 key/src, 작품, 실행 중 입력을 폭 변경 때문에 다시 불러오지 않습니다. 820px CSS/821px `matchMedia` 경계를 함께 유지합니다.
- 실습 진입은 탐색·단계 탭/제목의 초점을 빼앗지 않습니다. 수동 클릭·전환 버튼에서의 Escape는 전환 뒤 같은 버튼으로 초점을 돌립니다. 입력·캔버스·대화상자에서의 Escape를 전역 폭 복귀 단축키로 가로채지 않습니다.
- 숨겨질 탐색 안에 초점이 남은 경우에만 본문 또는 메뉴의 적절한 위치로 이동합니다. 실제 화면 갱신 뒤 Effect에서 처리합니다.

### 수업별 공간 배분

- **샌드위치:** 10/6 선생님의 원작 화면 비교 피드백이 기존320~400px 명령 폭·입력 우선 순서를 대체합니다. 901px 이상에서는 조리대:대화를 약2:1로 넓히고900px 이하에서는 세로로 배치합니다. 로봇 준비 안내→시간순 학생 명령/로봇 응답→하단 입력으로 구성합니다. 오른쪽 파랑 명령과 왼쪽 밝은 응답에 해석 출처를 표시하고, 대기/연결 실패/확인 질문에도 요청 원문을 함께 보여줍니다. 확인 질문·실패 대화는 화면을 열어둔 동안 보존하며 재접속에서는 기존 저장된 실행 명령을 복원합니다. 대화만 내부 스크롤하고 과거 대화를 읽는 위치는 유지합니다. 실행 기록은 주방과 대화 아래 두 열 전체를 차지합니다. 재실행·되돌리기는 기록의 ‘기록 도구’에 작게 접고, 새 레시피는 대화창 상단에 둡니다. 입력창은 한 줄 높이이고 ‘실행’ 버튼 또는 Enter로 보냅니다. Shift+Enter는 줄바꿈이며 한글 조합 확인 Enter는 전송하지 않습니다. AI 실패 때만 명시적인 ‘AI 없이 실행’을 제공하고 규칙 해석 출처를 유지합니다.
- **샌드위치의 그림과 낮은 창:** SVG의 빈 상단40을 덜고 재료·칼·엔진 좌표는 유지합니다. 최대 높이는450px,1440px 이상·높이800px 이하에서는400px로 하여1854×717에서도 조리대 실제 폭900px 이상을 확보합니다. 901~1439px·높이800px 이하에만190px 제한을 적용합니다. 1280×720·100% 확대·초기 실습·기본 넓음에서 별도 스크롤 없이 자연어 입력과 주 실행 버튼, 조리대 결과 안내를 함께 확인합니다. 이 낮은 창의 초기 대화는140px로 준비 안내 전체를 표시하고,실제 명령이 생긴 뒤에는240px에서 스크롤하며 모바일 대화는320px입니다. 200% 확대에서는 자연스러운 세로 스크롤과 읽기 순서를 검사합니다. 8종 상태는1440px 이상8열×1행,그 아래4열×2행,480px 이하2열×4행이며14px 이상의 글자를 유지합니다.
- **순서도:** 기존 기호 보관함·캔버스·실행 모니터와 퍼즐/자유 작품 구조를 유지합니다. 남는 폭은 캔버스에 우선 배분합니다. 내부 글자가 페이지 폭에 따라 계속 축소되지 않게 하고 캔버스 내부 스크롤을 사용합니다. 클릭·Enter로 선택/배치하는 기존 대안을 유지합니다.
- **추상화:** 워크북을 주 작업 영역으로 두고 AI 후보·상담/처방전은 보조 영역에 둡니다. 큰 화면의 두 작업 영역은 기존 흐름을 유지하고 좁은 화면에서는 현재 단계 입력 → 해당 도움/결과 순서로 배치합니다. 입력 라벨과 핵심/노이즈의 구분을 명확히 합니다.
- **EntryJS:** 최대 폭 제한과 외부 여백을 줄여 실제 편집기에 공간을 돌려줍니다. 저장·검증·제출 상태와 실행 결과는 작업실 근처에서 유지합니다. 기존 iframe 최소 폭1000px·높이660px/모바일620px를 출발점으로 유지하고, 화면을 맞추려고 전체 작업실을 작게 축소하지 않습니다. 낮은 창에서는 자연스러운 세로 스크롤을 허용합니다.

### 막혔을 때의 표시

학습상 오류는 무엇이 충족되지 않았는지와 다음 관찰/수정 지점을 보여줍니다. AI 지연·서비스 실패는 오답과 구분하고 현재 입력을 유지합니다. 저장 실패는 화면 이동 전에 해결하는 기존 안내와 재시도를 유지합니다. 새로운 범용 도움 창·튜터를 만들지 않고 기존 체험 재실행·힌트·작품 검증·교사 확인 경로를 연결합니다.

## 6. 구현 작업과 인터페이스

### 실행 단위와 진행 원칙

한 회차는 하나의 결과를 구현하고 다음 작업에 필요한 동작을 확인하는 작업 묶음입니다. **구현 회차는 1~12차로 유지하고, 넓은 회귀 검사·화면 행렬만 아래 통합 시점으로 묶습니다.** 현재 회차의 즉시 검사에 실패한 상태로 다음 회차를 시작하지 않습니다. 공통 컴포넌트의 계약 변경처럼 함께 고쳐야 컴파일되는 호출부는 한 회차에서 원자적으로 변경합니다.

이번에는 **대표 수업부터 확장하는 방식과 계층형 검증**을 적용합니다. 공통 상태·폭·초점의 오류를 대표 수업에서 먼저 발견하고, 실제 화면에서 확인한 패턴을 다른 수업에 적용하기 위해서입니다. 공통 부품의 호출부 호환성은 먼저 유지하되, 수업별 체험과 실습 배치는 해당 회차에서 완성합니다. 검증 범위를 줄여 문제를 숨기거나 요구사항을 생략하지 않습니다.

- 각 회차를 시작할 때 Git 상태와 앞 회차의 변경·검증 결과를 읽습니다. 기존 사용자 변경과 이번 회차 변경을 구분합니다.
- 기능 변경은 해당 실패 상황을 재현하는 검사를 먼저 마련하고 구현합니다. 단순 색상·문구 변경에는 구현을 복제하는 테스트를 만들지 않고 실제 화면과 기존 조작을 확인합니다.
- 작업 중에는 `typecheck`와 새 동작·중요 실패에 대한 해당 회차의 즉시 검사를 우선합니다. 공통 상태·셸 변경은 연결된 수업의 짧은 동작 검사도 남깁니다. 전체 파일의 긴 회귀 검사와 반복적인 화면 행렬은 아래 통합 시점으로 모읍니다.
- 회차 종료 시 변경 범위·실제 검사 명령/환경/결과·확인한 화면·미해결 사항·다음 회차를 기록합니다. 실행 상태는 아래 장부에서 관리하고, 세션을 마칠 때 현재 브랜치·미커밋·다음 행동을 `docs/HANDOFF.md` 첫머리에 반영합니다. 매 회차 별도 계획서를 만들지 않습니다.
- 검사가 실패하면 같은 조건에서 원인을 확인하고 수정·재검증합니다. 같은 실패가 세 번 남으면 가설과 접근을 재검토합니다. 저장/초점/설명 정확성의 문제가 남으면 의존하는 회차를 시작하지 않습니다.
- 결과를 검토 가능한 상태로 나누되 회차마다 커밋·전체 빌드·전체 E2E를 반복할 필요는 없습니다. 커밋·인계·PR 직전에는 프로젝트의 최종 통합 검증을 반드시 수행합니다. 7차에서 작업을 마치고 인계할 때도 이 검증을 수행합니다. 운영 배포는 후속 승인 범위이며 실제 배포 확인을 따로 기록합니다.

### 회차의 검증과 통과 절차

각 회차는 **요구사항 대조 → 구현 → 즉시 기술/브라우저 검사 → 변경 검토·근거 기록 → 진행 판정**의 순서로 진행합니다. 넓은 회귀 검사·화면 행렬은 아래 통합 시점에 수행합니다. 즉시 검사 통과와 통합 검증 완료를 구분합니다.

1. **시작 조건 고정:** 앞 회차의 결과·현재 Git 변경·이번 수락 조건을 확인합니다. 합성 학생의 시작 단계·답안·완료·작품 상태를 정해 기대 결과와 비교합니다. 서버/API/Firestore/문항 ID/채점 규칙이 이번 변경으로 바뀌지 않았는지도 확인합니다.
2. **즉시 기술 검사:** 앱 코드를 바꾼 회차는 `npm.cmd run typecheck`와 이번 새 동작·영향이 큰 실패에 대한 대상 검사를 실행합니다. 순수 엔진·AI 프로토콜·반 변경 계획에 영향이 있으면 `npm.cmd run test:review`도 실행합니다. 아래의 파일 이름은 검사 후보이며 매 회차 파일 전체를 실행하라는 뜻이 아닙니다.
3. **즉시 화면 확인:** 수정한 화면의 핵심 조작·실패/복원·초점을 주 화면 1440×900에서 확인합니다. 해당 변경의 경계가 낮은 창·821/820px·움직임 줄이기라면 그 조건도 즉시 확인합니다. 나머지 전체 크기/상태 조합과 반복 캡처는 통합 시점에 수행합니다. DOM에서 보인다는 판정만으로 입력이 화면 안에 있거나 글자가 읽힌다고 판단하지 않습니다. 새 브라우저 콘솔 오류와 잘린 글자·겹친 버튼·초점 손실이 없어야 합니다.
4. **변경과 근거 대조:** diff에서 요구 범위를 벗어난 변경·불필요한 의존성·저장/채점 변경을 확인하고 `git diff --check`를 실행합니다. 새 미추적 파일은 일반 diff에 나오지 않으므로 따로 읽습니다. 실제 검사 명령·종료 결과·날짜/환경·확인한 화면과 예상 결과·남은 한계를 기록합니다.
5. **진행 판정:** 다음 작업에 필요한 즉시 조건이 충족되고 관련 실패가 없으면 `진행 검증 통과`로 기록합니다. 통합 시점으로 옮긴 검사는 담당 시점과 함께 `통합 검증 대기`로 남깁니다. 1~6차는 이 상태를 구분해 기록한 뒤 다음 회차로 진행할 수 있습니다. **7차는 대기 중인 필수 검증까지 완료한 뒤에도 `휴먼 리뷰 대기`로 남기고 8차를 시작하지 않습니다.**

검사 상태는 `미실행`·`통과`·`실패`로 구분하고 각각 근거를 붙입니다. 환경 문제로 실행하지 못한 필수 검사를 통과로 세지 않습니다. 실패하면 **원인 확인 → 수정 → 같은 조건 재검증 → 영향 흐름 확인**을 반복합니다. 다음 회차가 성공하더라도 앞 회차의 실패를 상쇄한 것으로 처리하지 않습니다. 뒤 회차에서 앞 회차의 코드나 공통 부품을 다시 바꾸면 관련 완료 조건을 다시 검사하고 기존 결과를 갱신합니다.

### 검사 선택과 결과 재사용의 조건

- 새 검사 파일은 `concept-nav`·`algorithm-scene`·`quiz-nav`·`workspace-width`·`sandwich-layout` 등의 그룹으로 구현했습니다. `abstraction`·`flowchart`·`programming-readability` 확장 검사는8~10차에 추가합니다. `--grep`으로 해당 그룹/케이스를 선택하고 `--list`로 의도한 검사가 수집되는지 확인합니다. 0개 수집·모든 선택 검사의 skip을 통과로 세지 않고 `--pass-with-no-tests`를 사용하지 않습니다.
- 기존 검사는 제목과 **본문의 시작 조건·역할·행동·예상 결과**를 대조해 선택합니다. 예를 들어 6차의 복습 폭 검사는 `review-practice-ui`의 `세 실습의 넓게 보기` 케이스를 선택할 수 있습니다. 파일 전체를 실행해야 확인되는 부분은 통합 실행에 남깁니다. 실행 전 실제 변경 후 제목·선택 결과를 다시 확인합니다.
- 같은 시험에서 같은 역할·자료·조건·결과를 이미 확인했다면 한 실행 결과를 여러 요구사항의 근거로 연결할 수 있습니다. 검사 이름이나 파일이 같다는 이유만으로 포함 관계를 가정하지 않습니다. Entry와 샌드위치의 저장 실패, 821/820px와 200% 확대, 개발 앱과 빌드 앱은 서로 대신하지 않습니다.
- 근거에는 **요구사항/시나리오 → 검사 케이스와 관찰 결과 → 실행 시점의 소스·테스트 변경 상태/빌드 → 환경 → 결과 자료**를 연결합니다. 같은 자료를 다시 생성하지 않고 링크합니다. 이후 관련 코드·CSS·테스트·환경이 바뀌면 영향받는 근거를 다시 확인합니다.
- `typecheck`는 후속 구현이 의존하는 계약 오류를 일찍 발견하는 즉시 검사로 유지합니다. 최종 전체 E2E도 유지합니다. 7차 뒤 8~11차에 코드가 추가되므로 12차 실행은 변경된 최종 상태를 검증하는 별도 실행입니다. 휴먼 리뷰를 기다리는 동안 코드/환경이 바뀌지 않으면 7차 전체 검사를 다시 실행하지 않습니다.
- 통합 실행이 실패하면 실패 케이스와 영향 그룹부터 수정·재검증합니다. 인계 전 전체 통과 결과는 마지막 변경 상태와 맞아야 합니다. 전체 실행을 대체할 수 없는 수정이면 최종 전체 검사를 갱신합니다. 검증 범위를 낮추거나 실패 검사를 빼서 성공으로 만들지 않습니다.

### 7차 인계 검증과 휴먼 리뷰 경계

7차에서 세션을 마칠 때는 **`npm.cmd run lint`·`npm.cmd run build`·`npm.cmd run test:review` 후 `CI=1`의 빌드 앱에서 전체 E2E**를 수행합니다. 이번 1~7차는 공통 개념/퀴즈·셸·폭/초점이 여러 흐름에 영향을 주므로 대상은 **`npm.cmd run test:e2e` 전체 검사**로 정합니다. 개발 앱 전체 검사 뒤 같은 대표 기능을 프로덕션에서 다시 검사하는 두 번의 실행을 계획하지 않습니다. 이미 실행 중인 에뮬레이터와 빌드 앱의 demo 설정/fixture를 확인한 경우에만 `test:e2e:running`으로 동일 범위를 검사합니다. 시각·실제 200% 등 자동 검사에 없는 항목은 같은 빌드 환경에서 보완합니다. 상세 실행 환경은 7절과 DEVELOPMENT의 기준을 따릅니다.

초기 7차의 결과물은 **1~7차 구현·기술 검증 완료 / 대표 수업 휴먼 리뷰 대기 / 8~12차 미착수**로 구분했습니다. 이후 선생님 피드백·수정과 확장 승인을 반영한 현재 상태는 아래 완료 장부를 따릅니다. 당시 검토 자료에는 다음을 포함했습니다.

- 대표 수업을 열어 개념 체험 → 퀴즈 → 실습 → 개념 복귀를 확인할 조작 순서와 합성 자료만 담은 화면 자료
- 기술 검증의 실제 결과·현재 브랜치/미커밋·변경 범위·남은 한계
- 판단할 세 가지: **강조와 읽기 편함**, **체험/설명이 중학생에게 명료한지**, **목표·첫 행동·결과·재시도 흐름이 자연스러운지**

2차의 시각적 인상과 4차의 교육적 표현은 대표 수업이 완성된 7차에서 함께 검토합니다. 선생님께서 확인하시기 전에는 8차 이후 확장을 시작하지 않습니다. 수정 의견이 있으면 관련 회차의 구현과 검증을 갱신한 뒤 다시 검토 자료를 남깁니다. 휴먼 리뷰는 기술 검사의 대체가 아니며 실제 학생의 학습 효과를 자동 테스트나 교사 화면 검토만으로 입증하지 않습니다.

### 회차별 범위와 다음 단계로 넘어가는 조건

**1차 — 구현 전 기준 확인**

- Git 브랜치·기준 커밋·미커밋 파일과 실행 중인 서버를 확인하고 이번 작업의 변경 범위를 기록합니다. 실제 구현 시작 시의 상태를 다시 확인하며 계획 작성 당시의 상태를 그대로 가정하지 않습니다.
- PRD·DESIGN·DEVELOPMENT의 관련 절과 실제 컴포넌트·기존 테스트를 읽습니다. 운영 4개 수업의 개념/퀴즈/실습, 공개 프로토타입과 기존 EntryJS의 공유 경로를 확인합니다.
- 합성 계정으로 대표 화면을 확인합니다. 주 화면 1440×900과 낮은 창 1280×720에서 현재 카드·여백·샌드위치 입력 위치를 기준 자료로 남기고, 기존 답안/작품의 단계 왕복·재접속을 확인합니다. 저장 실패·충돌에 대한 기존 검사의 위치와 실행 환경도 확인합니다.
- **완료 조건:** 사용할 로컬 환경·보존해야 할 상태·수정 대상·기준 화면이 확인됩니다. 기존 실패가 있으면 변경으로 생긴 실패와 구분해 기록하고 관련 작업을 시작하기 전에 해결 방향을 정합니다. 앱 기능은 아직 변경하지 않습니다.

**2차 — 색상과 읽기 기준을 대표 화면에 적용**

- 작업1의 세 전역 토큰을 추가하고 알고리즘 설계의 개념 영역에만 우선 사용합니다. 본문·제목·조작·보조 정보의 크기와 대비를 확인합니다.
- 홈·대시보드·다른 수업의 색상 적용은 11차 및 각 수업 회차로 남깁니다. 기존 전역 버튼 토큰을 일괄 변경하지 않습니다.
- **즉시 검증:** `typecheck`, 대표 개념의 주 화면·Tab·44px 조작 영역·실제 사용 색의 대비를 확인합니다. 전체 화면 크기/긴 문구의 검토는 5차에 통합합니다.
- **완료 조건:** 파란 주요 조작과 따뜻한 예시/설명이 구분되고 긴 설명을 읽을 수 있습니다. 공통 토큰 추가가 다른 역할의 색이나 배치를 바꾸지 않습니다.

### 검사 실행

새 `tests/learning-readability.spec.ts`는 기존 에뮬레이터 helper와 합성 학생20102를 사용합니다. 각 검사 전에 필요한 로컬 반2-1 설정을 보존하고, 검사 뒤 반 설정과 테스트 작업 문서를 정리합니다. 앱 콘솔의 새 오류를 확인하며 운영 계정·작품을 사용하지 않습니다.

작업 중에는 `npm.cmd run typecheck`와 해당 그룹/케이스만 실행합니다. 이미 확인한 로컬 에뮬레이터·앱·fixture가 실행 중이면 `npm.cmd run test:e2e:running -- tests/learning-readability.spec.ts --grep "concept-nav"`처럼 지정합니다. 없으면 대상은 Firebase CLI 인자가 아니라 `emulators:exec` 안의 Playwright 명령에 넣습니다. 아래 예시는 3차의 새 그룹을 작성한 뒤 사용하는 명령입니다.

```powershell
npx.cmd firebase emulators:exec --only auth,firestore --project demo-cs-class "playwright test tests/learning-readability.spec.ts --grep concept-nav"
```

7차 최초 인계와12차 최종에는 각각 `npm.cmd run lint`·`npm.cmd run build`·`npm.cmd run test:review` 후 `CI=1`로 `npm.cmd run test:e2e` 전체 E2E를 빌드 앱에서 실행합니다. 최초1~7차는 공통 셸·수업에 걸쳐 있어 통합 범위를 전체로 정했습니다. 10/6 휴먼 리뷰의 후속 수정은 샌드위치 부품과 해당 범위의CSS에 한정되어,typecheck/lint/build와 빌드 앱 영향10개를 새로 검사합니다. 공유 스타일 파일을 사용하는 추상화·순서도의 기존 조작/폭/초점/콘솔 검사도 포함합니다. 최초 전체 결과는 과거 근거로만 남기고 새 전체 실행으로 표현하지 않습니다. 공통 계약이나 더 넓은 화면을 바꾸면 영향을 다시 산정합니다. 포트·demo 환경·Java·캐시는 [개발 안내](../DEVELOPMENT.md#다른-pc에서-시작)에 따라 확인하고 준비 환경을 재사용합니다.

기존 `scripts/dev-emulator.mjs`는 `CI=1`이면 `next start`로 실행합니다. 빌드 성공을 확인하고 같은 검사 터미널에 `$env:CI="1"`을 설정해 전체 검사를 에뮬레이터 안에서 실행한 뒤 CI 값을 원래대로 복원합니다. 확인된 개발 앱 테스트 서버는 빌드 앱으로 전환하며 기존 개발 서버를 빌드 검증으로 간주하지 않습니다. 기본 config의 시간표 fixture와 로컬 Cron 검사용 값·demo 준비 흐름을 재사용합니다. 같은 빌드 환경에서 대표 수업·샌드위치·공유 프로토타입·포털의 CSS를 확인하되, 전체 실행이 이미 확인한 기능/화면의 동일 검사를 따로 반복하지 않습니다. 자동 검사에 없는 시각·실제 200%·읽기 확인과 필요한 합성 화면 캡처만 보완하고 `scratch/`에 보관합니다.

## 8. 설계 판단의 근거

- [IES: Organizing Instruction and Study to Improve Student Learning](https://ies.ed.gov/ncee/wwc/PracticeGuide/1)는 설명과 그래픽, 예제와 문제 풀이를 연결하는 방향의 참고입니다. 이 프로젝트에서의 효과를 보장하는 근거로 사용하지 않습니다.
- [W3C: Provide Feedback](https://www.w3.org/WAI/WCAG2/supplemental/patterns/o4p10-status-feedback/)에 따라 학생 행동의 처리 결과와 다음 행동을 분명히 표시합니다.
- [W3C: Contrast Minimum](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)을 기준으로 실제 사용 색 조합의 대비를 확인합니다.
- 계획 작성 중 설치된 Next.js의 CSS Module/프로덕션 CSS 순서 안내와 Context7의 React19.2.8 상태 보존/Effect 문서를 확인했습니다. 구현 중 라이브러리/API 사용이 달라지면 해당 버전의 관련 문서를 추가로 확인합니다.
