# 컨설팅 후속 개선 Implementation Plan

> **실행 기준:** 승인된 계획의 구현에는 `superpowers:executing-plans`를 적용합니다. 아래 상태는 제안 작성·구현 승인·실제 병합/배포 승인을 구분합니다. 2026-10-10 받은 실제 GitHub/Vercel 대상 승인은 [R9](#r9-운영-반영과-학교-환경-리허설)에 기록하며, 과거 회차의 구현 승인 범위를 확대하지 않습니다.

**Goal:** 학생의 다음 행동과 학습 상태를 명확히 하고, 교사의 확인 흐름을 개선하면서 기존 저장·권한·수업 정책을 보존합니다.

**Architecture:** 기존 `useWork`, `LessonShell`, `ClassProgress`, `progressFor`와 교사 조회 응답을 재사용합니다. 화면 변경·실패 복구·코드 이동을 별도 검토 가능한 작업으로 나누고, 같은 파일은 순차적으로 통합합니다. 새 의존성·DB 스키마·범용 수업 엔진을 추가하지 않습니다.

**Tech Stack:** 현재 Next.js 16.3.6·React 19.2.8·TypeScript·CSS Modules·Firebase Auth/Firestore·Playwright를 유지합니다.

**Spec:** [컨설팅 보고서의 9개 제안](project-consulting-2026-10-08.md#먼저-검토할-제안). 확정 정책은 [PRD](../PRD.md), 시각·상호작용은 [DESIGN](../DESIGN.md), 검증 절차는 [AGENTS](../../AGENTS.md)와 [DEVELOPMENT](../DEVELOPMENT.md)를 따릅니다.

## Global Constraints

- 수업 내용·문항 ID·선택지·정답·채점 회차 정책을 변경하지 않습니다.
- 학생 수업은 `LessonShell`, 대시보드·교사 화면은 `AppShell`을 사용합니다.
- `useWork`의 단일 저장 소유권, 입력 보존·충돌 비교·이전 제출본 보존을 유지합니다.
- 기존 단계 자유 이동, 선택 복습/도전의 완료율 계산, 30초 교사 조회와 수동 새로고침 정책을 유지합니다.
- 기본 1280×720·100% 배율에서 대표 퀴즈의 문제·선택지·주행동을 함께 보이게 하는 것을 목표로 합니다. 좁은 창·확대·긴 해설에서는 세로 스크롤을 허용합니다.
- 검사는 `demo-cs-class`와 로컬 Auth 9099·Firestore 8080만 사용하며 앱 주소는 `http://localhost:3000`으로 통일합니다.
- 운영 데이터·학생 개인정보·비밀정보를 검사나 캡처에 사용하지 않습니다. 기존 미커밋·미추적 보고서와 캡처를 보존합니다.
- 실행 시 `codex/` 브랜치를 사용하고, 외부 라이브러리/API 구현에 실제로 손대는 경우 설치 버전의 로컬 문서와 Context7을 확인합니다.
- 앱 코드를 작성하기 전에는 해당 Next.js 가이드를 `node_modules/next/dist/docs/`에서 확인합니다.

## 추천 순서와 이유

컨설팅 표의 번호는 제안 식별자입니다. 사용자 영향이 큰 항목의 순위와 실제 구현 순서는 다릅니다. 먼저 국소적인 상태 불일치를 고치고, 실패 복구를 정리한 뒤 그 상태를 담을 퀴즈 화면을 완성하는 편이 재작업이 적습니다.

| 회차 | 원 제안 | 최소 결과물 | 규모 | 이 순서인 이유 |
|---|---|---|---|---|
| 1차 | 2·3 | 이번 수업과 그래프의 대상 일치, 제출 수에 근거한 실습 상태 | S | 기존 데이터로 고칠 수 있고 효과·검증이 명확함 |
| 2차 | 4 | 저장 실패와 행동 결과 불확실성의 구분·복구 | M | 퀴즈/실습 화면에 들어갈 오류와 재시도 계약부터 안정화 |
| 3차 | 1 | 대표 퀴즈의 문제·선택·다음 행동을 함께 보는 배치 | M | 2차의 실제 실패 상태까지 포함해 화면을 완성 |
| 4차 | 6→5 | 최근 제출 학생, 선택 반·수업의 확인 요청 조건과 작품 조회 | S+M | 같은 홈 파일을 순차 수정하고 요청 필터의 창 보존까지 검증 |
| 5차 | 7 | 확장 효과가 있는 경우의 넓게 보기와 안전한 복귀 | S | 새 집중 모드를 만들기 전에 기존 버튼의 의미부터 맞춤 |

## 2차: 실패 복구 정리 — 제안 4

## 검증·작업 운영

구현 시작 시 현재 Git 상태와 실제 대상 파일을 다시 확인하고, 1차부터 독립 검토 가능한 커밋 단위로 진행합니다. 파일 이동은 사용자 동작 변경과 분리합니다. 공유 화면은 순차 통합합니다. 이동처럼 독립된 파일은 담당 범위를 명시해 병렬 구현하고, `lesson-workspace.tsx`나 공통 홈 파일의 동시 편집은 피합니다. 검사는 단일 worker로 직렬 실행합니다.

- 반복 수정: `npm.cmd run typecheck`와 변경한 대상의 단일 검사. 이미 로컬 에뮬레이터가 실행 중일 때만 `npm.cmd run test:e2e:running -- tests/<target>.spec.ts`를 사용합니다.
- 에뮬레이터가 없을 때 대상 검사는 `npx.cmd firebase emulators:exec --only auth,firestore --project demo-cs-class "npx.cmd playwright test tests/<target>.spec.ts"`로 시작합니다. 대상 인자는 Firebase CLI 바깥에 덧붙이지 않습니다. 기존 포트/서버와 demo 프로젝트를 먼저 확인하고 fixture·공유 반 설정을 검사 후 복원합니다.
- 회차 통합: `npm.cmd run lint`, `npm.cmd run build`, 해당 회차의 영향 E2E. 공용 부품은 사용하는 흐름을 함께 검사하고 영향이 전체이면 전체 E2E를 실행합니다. 새 실패·변경이 없으면 무관한 전체 검사를 반복하지 않습니다.
- 2차의 공유 저장 경계와 6차/9의 공통 변경까지 모두 채택했다면 마지막에는 로컬 demo 환경의 전체 `npm.cmd run test:e2e`를 단일 실행으로 확인합니다. 이후 기능 변경이 없을 때 같은 전체 검사를 반복하지 않습니다.
- 회차가 끝날 때 실제 환경·날짜·검사 범위·남은 한계를 HANDOFF에 기록합니다. 승인된 정책/디자인 변경만 PRD/DESIGN에 반영하고, 이 제안 문서의 대안을 확정 정책으로 복사하지 않습니다.

실행 방식은 **주 에이전트가 공유 파일을 순차 구현하고, 저장 복구·교사 작품 창·최종 통합에는 독립 리뷰를 붙이는 방식**을 권합니다. 모든 작은 CSS 변경마다 새 작업자/리뷰어를 만들기보다, 상태·권한·입력 보존의 위험이 있는 경계에 비용을 집중합니다.
