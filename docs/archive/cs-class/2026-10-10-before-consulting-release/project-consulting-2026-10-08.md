## 종합 판단

**기반은 합리적입니다. 전면 재설계할 프로젝트는 아닙니다. 다만 기능의 완성도에 비해 상태를 해석하고 다음 행동을 찾는 경험이 덜 정리돼 있습니다.**

파일이 많다는 이유로 구조가 나쁘다고 판단할 근거는 없습니다. 기능별 폴더와 화면 옆 CSS, 얇은 URL 진입점, 서버·클라이언트 경계는 대체로 적절합니다. 실제 구조 문제는 과도한 원자화보다 **운영과 체험의 소유권 혼재, 큰 수업 편집기의 책임 집중, 교체 후 남은 스타일**입니다.

학생 화면의 가장 큰 개선 대상은 퀴즈입니다. 한 문제씩 보여주면서도 문항 목록·누적 상태·문제·장면·선택지·힌트·이동·회차 결과를 세로로 모두 쌓습니다. **한 문제 집중형이라는 기능과 한 화면 집중형이라는 경험은 다릅니다.** 현재는 전자는 구현됐고 후자는 부족합니다.

교사 화면은 조회와 보존에 강합니다. 반면 확인 요청·새 제출·수업 준비 누락을 빠르게 찾아 처리하는 흐름은 보강할 여지가 있습니다. 여기서 필요한 것은 대시보드 장식 추가보다 **어떤 수업의 누구에게 어떤 행동이 필요한지 명확히 하는 것**입니다.

### 근거의 구분

- **실측:** 이번 로컬 브라우저에서 직접 재현하거나 크기를 측정했습니다.

- **사용성 가설:** 학생·교사가 실제로 불편해할 가능성입니다. 실사용 관찰 전에는 사실로 단정하지 않습니다.
- **대안:** 채택 여부와 정책 변경 여부는 선생님께서 결정하실 내용입니다.

## 2. 학생의 이용 경험

### S1. 실습 진행 상태가 실제 활동을 설명하지 않습니다 — 실측, S

수업을 시작한 뒤 **퀴즈 탭만 선택했는데 실습 탭은 ‘진행 중’으로 바뀌었습니다.** 일반 수업과 프로그래밍 수업에서 모두 확인했습니다. [lesson-workspace.tsx 161줄](../../src/components/student/lesson-workspace.tsx)은 실습 고유 기록 대신 수업 전체 `work.updatedAt`으로 이 문구를 결정합니다.

실습 시작을 판단할 수 있는 실제 근거를 쓰거나 `0/4개 제출`처럼 확인 가능한 수치만 표시하는 안을 권합니다. 활동 시작 여부를 알 수 없는데 친절한 문구를 만들기 위해 추정하면 상태에 대한 신뢰가 떨어집니다.

### S2. 저장과 요청 실패의 의미를 분리해야 합니다 — 코드 확인, M

[use-work.ts 109~115줄](../../src/components/student/use-work.ts)은 초안을 저장한 뒤 채점·검증 등의 action을 실행합니다. action 실패도 같은 `fail` 경로를 통해 저장 실패 상태가 됩니다. 화면의 `저장 다시 확인`은 초안 flush를 재시도하고 원래 채점 동작을 다시 실행하는 버튼은 아닙니다.

답안은 저장됐고 채점만 실패한 경우라면 `답안 저장 완료 · 채점 실패`와 `채점 다시 시도`가 정확합니다. 검증·제출도 같은 원칙이 필요합니다. **데이터 손실이 확인된 것은 아닙니다. 보존은 신중한데 안내가 실패 대상을 정확히 설명하지 못하는 문제**입니다. 응답이 불확실한 요청의 중복 방지까지 보존해야 하므로 문구 교체만으로 끝날 작업은 아닙니다.

### S3. 단계 이동의 대기 이유를 보여줄 수 있습니다 — 코드 확인·사용성 가설, S→M

단계 이동은 최신 입력 저장과 선택 단계 저장을 마친 뒤 화면을 바꿉니다. 안전한 정책입니다. 다만 느린 학교망에서는 탭이 반응하지 않는 것처럼 느껴질 수 있습니다. 선택한 탭에 `저장 후 이동 중`을 잠깐 표시하는 작은 개선부터 권합니다.

낙관적으로 먼저 이동하는 설계는 저장 실패 복귀와 Entry 입력 확정까지 필요합니다. 실제 지연을 측정하기 전에 도입할 이유는 부족합니다.

### S4. 이어하기의 복원 범위를 설명하면 됩니다 — 정책 확인, S

새로고침·재접속 시 개념은 첫 미완료, 퀴즈는 첫 미답변 또는 오답부터 시작합니다. 같은 화면에서 왕복할 때의 선택 위치와 정확히 읽던 위치의 영구 복원은 다릅니다. 이는 [PRD](../PRD.md)에 명시된 정책이며 고장이 아닙니다.

필요하다면 `남은 개념부터 이어해요` 같은 짧은 설명으로 복귀 이유를 알려줄 수 있습니다. 정확한 위치 저장은 학생이 실제로 요구하는지 확인한 뒤 별도 저장 모델 변경으로 검토하십시오.

### S5. 모바일에서는 다음 행동을 진도보다 먼저 놓는 대안이 있습니다 — 실측·사용성 가설, S~M

390×720의 학생 홈에서 이번 수업 미지정 상태의 `열린 수업 보기`는 y=767~813으로 첫 화면 밖에 있었습니다. 390×844에서는 같은 버튼이 보입니다. 앞의 환영 제목·날짜·큰 진도 링이 수직 공간을 차지합니다. [캡처](consulting-20261008/student-dashboard-390x720.png)

현재 진도 링은 사용자가 합의한 주시각 요소이므로 삭제할 이유가 없습니다. 다만 모바일에서 **이번 수업과 진입 버튼을 먼저, 원형 진도를 그 아래 또는 작은 요약으로** 두는 대안은 검토할 만합니다. 학생이 등교 후 수업을 시작하는 속도와 진도에 대한 관심 중 무엇을 더 우선할지 선택하는 디자인입니다. 데스크톱까지 전면 교체할 필요는 없습니다.

### S6. 전체 완료율 하락은 계산 오류가 아니라 해석 위험입니다 — 실측·합의 정책, 선택 S

같은 완료 3개를 유지한 채 정규 수업 하나를 더 열자 전체 완료율은 `3/18 = 17%`에서 `3/31 = 10%`로 바뀌었습니다. 선택 복습은 분모에 들어가지 않았습니다. 이는 현재 열린 정규 수업 기준이라는 [기존 합의](../PRD.md)의 정확한 동작입니다.

학생이 기록이 사라졌다고 오해할 가능성은 있습니다. 계산을 바꾸기보다 원하면 읽는 설명이나 새 정규 수업 공개 시 `완료 기록은 그대로이며 열린 활동이 늘었어요` 같은 안내를 검토하십시오. 상시 범위 문구를 숨긴 기존 DESIGN 합의도 있으므로 설명을 무조건 다시 늘리는 것은 권하지 않습니다.

### S7. 복습의 제출 완료는 제출이라고 표현하는 편이 정확합니다 — 코드 확인, S

Entry 실습은 저장·검증·제출을 구분합니다. 반면 [복습 공통 영역](../../src/components/student/review/shared.tsx)은 제출 완료를 `복습 작품을 저장했어요`라고 표현합니다. 자동 저장과 실제 제출에 모두 저장 표현을 사용합니다. 두 행동을 혼동할 가능성이 있습니다.

`제출 완료`, `제출 전 검증 필요`, `수정한 작품 다시 검증 필요`처럼 짧은 상태로 맞추는 안을 권합니다. 이 때문에 안내 카드를 더 추가하지는 마십시오. 정보가 정확해지는 것과 화면이 길어지는 것은 별개입니다.

## 3. 교사의 이용 경험

### T1. 이번 수업 미지정과 그래프 대상이 어긋납니다 — 실측, S

`currentLessonId=null`이며 열린 정규 수업과 등록 학생이 있는 상태에서 교사 홈은 `이번 수업을 지정해 주세요`라고 표시하면서 첫 열린 수업의 완료율 25%, 필수 활동 3/12를 보여줬습니다. [캡처](consulting-20261008/teacher-no-current-graph-1280x720.png)

서버 [classroom.ts 99줄](../../src/lib/server/classroom.ts)은 첫 열린 수업을 대체 조회 대상으로 사용합니다. 공통 [dashboard.tsx 54~66줄](../../src/components/dashboard/dashboard.tsx)은 제목과 그래프를 서로 다른 기준으로 렌더링합니다. **집계 오류가 아니라 카드 제목과 조회 대상의 표현 불일치**입니다. 아래 학습 현황 링크에는 대상 수업명이 있어 혼동을 일부 완화하지만 같은 카드의 의미는 여전히 모호합니다.

가장 작은 해결은 그래프에 `조회 중: ○○ 수업`을 붙이는 것입니다. 더 명확한 대안은 이번 수업 카드에서는 미지정 안내만 표시하고, 대체 수업 현황은 아래 조회 영역으로 옮기는 것입니다.

### T2. 확인 요청을 처리할 일로 연결하십시오 — 코드 확인·사용성 가설, S→M

학생이 제출 전에 `선생님 확인 요청`을 보낼 수 있지만 교사 홈의 작품 바로가기는 제출 작품이 있는 학생 중심입니다. 확인 요청은 상세 학생 행의 배지·버튼에서 찾고, 진행 필터에는 별도 조건이 없습니다. [교사 목록](../../src/components/teacher/dashboard.tsx), [작품 대화상자](../../src/components/teacher/dialogs.tsx)

먼저 선택 수업의 `확인 요청 ○건`과 해당 학생 목록으로 가는 필터 링크를 추가하는 작은 안을 권합니다. 다음 단계로 요청 시각순 목록에서 작품을 바로 열 수 있습니다. 손들기와 작품 승인 요청은 목적과 처리 행동이 다르므로 이름만 합쳐 하나의 요청으로 만들면 안 됩니다.

모든 반·모든 수업·Q&A를 한 통합함으로 읽는 기능은 별도 L 작업입니다. 첫 개선부터 그렇게 키울 필요는 없습니다.

### T3. 제출 바로가기는 최근 제출을 보여주는 편이 낫습니다 — 코드 확인, S

서버의 학생 목록은 학번순이고 홈은 제출 학생의 앞 3명을 표시합니다. 낮은 학번의 같은 학생들이 계속 노출될 수 있습니다. 제출 시각 데이터는 이미 있습니다. [dashboard.tsx 72줄](../../src/components/dashboard/dashboard.tsx)

학생별 최근 제출 시각으로 정렬하고 `최근 제출`이라고 명명하는 안을 권합니다. 대안은 3개 링크를 없애고 `제출 학생 ○명 보기`로 단순화하는 것입니다. `미열람`은 현재 기록하지 않는 상태이므로 추정해서 표시하면 안 됩니다.

### T4. 손들기는 맥락과 확인 시점을 더 가까이 보여줄 수 있습니다 — 코드 확인·실측, S

손들기 목록은 반 전체 수업을 가져오지만 행에는 학생·단계·시각 중심으로 표시합니다. 수업명·미션은 작품을 열어야 확인합니다. 여러 수업을 병행하면 현재 수업의 요청으로 오해할 수 있습니다. [help-requests.tsx](../../src/components/classroom/help-requests.tsx)

행에 짧은 수업명·학습 위치와 패널의 마지막 확인 시각을 추가하는 안을 권합니다. 1280×720 초기 교사 홈에서 손들기 제목은 y=892로 첫 화면 밖에 있었습니다. 긴급 요청이 있을 때 상단 건수·이동 링크만 보여주는 대안도 있습니다. **교사 홈의 기존 순서는 이미 수업·학습 확인을 개인 할 일보다 앞세웁니다. 전면 재정렬이 필요하다는 주장은 하지 않습니다.**

30초 조회를 곧바로 실시간 구독으로 바꾸기보다 실제 수업에서 이 지연이 대응을 막는지 확인하십시오. 필요할 경우 작은 요청 목록만 먼저 검토하면 됩니다.

### T5. 수업 준비용 미리보기와 반별 설정 표가 유용할 수 있습니다 — 코드 확인·가설, M

교사는 실제 학생 수업 경로에 학생 권한으로 접근할 수 없습니다. 공개 explore는 소개이며 실제 학습 화면과 동일한 경험이 아닙니다. 수업 관리의 열린 수업 카드도 제목·설명 중심입니다. **수업을 가르치는 사람이 학생의 버튼과 단계 흐름을 빠르게 볼 경로가 약합니다.**

작은 대안은 기존 공개 체험 링크를 제공하고 실제 수업과 다른 소개라는 점을 명시하는 것입니다. 더 완전한 대안은 실제 수업 부품을 재사용하는 교사용 체험으로, 학생 제출·손들기·실제 학습 기록을 만들지 않는 저장 경계가 필요합니다. 학생 계정을 가장하는 방식이나 새로운 콘텐츠 편집기는 필요 없습니다.

11반의 준비 여부는 한 반씩 선택하며 기억해야 합니다. 이미 조회하는 반 설정을 활용해 `반 / 이번 수업 / 열린 수업 수 / 설정 열기` 표를 먼저 만들 수 있습니다. 일괄 공개·지정은 충돌·대상 확인·부분 실패를 다뤄야 하므로 이 표를 써 본 뒤 결정하는 편이 낫습니다.

### T6. 이미 공개한 수업을 되돌릴 수 없다는 정책을 저장 전에 더 명확히 알릴 수 있습니다 — 코드 확인, 선택 S

수업 관리에서 이미 열린 수업의 체크박스는 비활성화됩니다. 기존 복습과 기록을 유지하는 정책입니다. 그러나 처음 여는 수업은 체크 후 설정 저장으로 공개되고, 이후에는 같은 화면에서 닫을 수 없습니다. [dialogs.tsx 56~59줄](../../src/components/teacher/dialogs.tsx)

‘미리 보고 싶어서 체크했다’ 같은 착오가 걱정된다면 저장 직전 요약에 `새로 공개할 수업`과 `현재 화면에서 공개를 취소할 수 없음`을 짧게 보여줄 수 있습니다. 매번 확인창을 하나 더 만드는 것보다 현재 모달 안의 요약이 낫습니다. 공개 취소 기능 자체를 만들지는 선생님의 운영 정책 결정입니다.

### T7. 검색 대상과 목록의 표시를 맞추십시오 — 코드 확인, S

학생 행은 닉네임을 크게 보여주지만 검색은 학번만 검사합니다. 기존 학번·닉네임 모두 검색하고 라벨도 맞추면 학생 찾기가 쉬워집니다. 실명 수집은 필요하지 않습니다. `비밀번호 변경 필요 ○명` 조건도 첫 입장 지원에 유용할 수 있습니다. 다만 비밀번호 변경 필요를 출석 실패나 접속 장애라고 단정하면 안 됩니다. [teacher/dashboard.tsx 96·191줄](../../src/components/teacher/dashboard.tsx)

### T8. 질문 필터의 빈 상태는 조회 범위를 밝혀야 합니다 — 코드 확인, S 또는 M

Q&A는 최근 50개를 가져온 뒤 화면에서 `답변 대기 / 해결됨`을 거릅니다. 그 50개에 없고 다음 페이지에 해당 질문이 있어도 `해당하는 질문이 없어요`라고 표시할 수 있습니다. 이전 질문 더 보기는 남아 있어 찾는 기능이 사라진 것은 아닙니다. [community.tsx 169·184~188줄](../../src/components/community/community.tsx), [서버 조회](../../src/lib/server/community.ts)

`조회한 최근 ○개에서 결과 없음 · 이전 질문 더 보기`로 범위를 밝히는 작은 안이 충분합니다. 모든 질문 기준의 정확한 상태 필터가 필요하면 서버 질의·인덱스·cursor에 반영하는 M 작업으로 나누십시오. 학생 답변이 달린 미해결 질문까지 챙기려면 `답변 없음`과 `미해결`의 의미도 구분해야 합니다.

## 4. UI·UX에 줄 포인트와 덜어낼 요소

**더할 포인트는 장식보다 행동의 의미입니다.** 현재 파랑·한국어 글꼴·밝은 표면과 역할별 셸은 일관됩니다. 사이트의 정체성을 다시 만들 필요는 없습니다.

| 더 분명하게 만들 것 | 덜어내거나 접을 것 | 유지할 것 |
|---|---|---|
| 현재 문항과 다음 행동의 위치 | 해결 수의 여러 위치 반복 | 큰 한국어 본문과 선택 영역 |
| 실제 제출 완료·검증 필요 상태 | 마지막 문항 전부터 항상 큰 회차 결과 카드 | 접힌 힌트와 해설을 읽는 시간 |
| 교사의 확인 요청·최근 제출 | 처리할 일과 무관한 고정 3명 링크 | 반 맥락 유지와 정확한 제출 단위 |
| 작은 창의 수업 시작 버튼 | 좁은 창의 긴 환영 영역·큰 문항 목록 | 사용자가 선택한 진도 링의 의미 |
| 저장/행동 실패별 복구 버튼 | 같은 문구·숫자의 중복 강조 | 실패 시 입력 보존·충돌 비교 |

현재 UI에 모션·캐릭터·차트 색을 더 넣는 것이 급한 일은 아닙니다. 공개 홈은 수업을 소개하는 표현이 필요하고, 작업 화면은 입력과 판단이 우선입니다. 이미 공개 홈 상단 입장 버튼과 역할 선택이 있으므로 홍보 페이지를 전면 교체할 이유도 없습니다.

큰 여백 자체가 나쁜 것은 아닙니다. **정보 사이의 관계를 보여주는 여백은 남기고, 조작을 화면 밖으로 밀어내는 반복 여백부터 줄이는 것**을 권합니다. 글자나 클릭 영역을 작게 만들어 높이만 맞추는 방식은 피하십시오.

## 5. 수업 틀과 퀴즈의 스크롤

### 수업 틀의 큰 동작은 자연스럽습니다

개념→퀴즈→실습이라는 안내 순서와 자유로운 단계 이동이 함께 있습니다. 앞 단계 완료로 다음 입장을 막지 않고, 채점 후 자동으로 다음 화면을 넘기지 않습니다. 조회 대기·실패에도 수업 상단을 유지하고 나가기·학생 메뉴를 보존하는 구조가 좋습니다. 저장→검증→제출과 이전 제출본 보존도 유지해야 합니다.

이번 일반 퀴즈에서는 세 답을 선택하고 회차 결과를 확인했으며 다음 문항 이동 시 문항 제목으로 초점이 이동했습니다. 결과 확인 후에도 결과 영역으로 초점이 옮겨졌습니다. 저장 후 나가기로 수업 목록·홈에 복귀하는 흐름도 확인했습니다.

### Q1. 스크롤에 관한 선생님의 문제 제기는 타당합니다 — 실측

힌트와 수업 상세 안내를 닫고 첫 문항을 보여준 상태입니다. y는 해당 화면의 위쪽을 0으로 한 CSS px 위치입니다.

| 실제 수업 | 창 | 문서 높이 | 다음 문제 | 회차 결과 확인 |
|---|---|---:|---:|---:|
| 일반 순서 수업 | 1280×720 | 1,128px | y=791~840 | y=1021~1070 |
| 프로그래밍 수업 | 1280×720 | 1,202px | y=901~946 | y=1007~1054 |
| 프로그래밍 수업 | 1440×900 | 1,202px | y=901~946 | y=1007~1054 |
| 프로그래밍 수업 | 390×844 | 1,512px | 첫 화면 밖 | 첫 화면 밖 |

[일반 퀴즈 캡처](consulting-20261008/sequence-quiz-1280x720.png), [프로그래밍 캡처](consulting-20261008/programming-quiz-1280x720.png), [좁은 창 캡처](consulting-20261008/programming-quiz-390x844.png)

일반 퀴즈는 헤더 90px, 단계 탭 48px, 접힌 안내를 지난 뒤 퀴즈 영역이 y=215에서 시작합니다. 문항 목록·단계 제목·설명까지 지나 문제 카드는 y=390입니다. 프로그래밍 퀴즈는 390px에서 문항 목록만 세 줄입니다. 세부 진도를 이미 접어 두었는데도 이런 결과가 나옵니다.

**‘한 화면에서 문제를 읽고 답을 고르고 다음으로 갈 수 있게 하자’는 방향에 동의합니다. ‘어떤 조건에서도 스크롤을 금지하자’는 목표에는 동의하지 않습니다.** 긴 한글 선택지·해설·오류·확대에서는 세로 스크롤이 필요할 수 있으므로 허용해야 합니다. `overflow:hidden`으로 숨기는 방식은 개선이 아닙니다.

W3C의 [Reflow 설명](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html)은 정보를 잃지 않는 재배치를 다루며 세로 스크롤 자체를 금지하지 않습니다. 고정 행동 바를 쓰면 [키보드 초점 가림](https://www.w3.org/WAI/WCAG22/Understanding/focus-not-obscured-minimum.html)도 함께 확인해야 합니다.

### Q2. 세 가지 대안

| 안 | 구체적인 구성 | 장점 | 대가·주의 | 규모 |
|---|---|---|---|---|
| A. 현재 세로 배치를 다듬기 | 짧은 문항 칩, 해결 수 중복 제거, 문제·선택지 여백 절제, 이동·채점 행동 한 행 | 가장 싸고 기존 흐름 유지 | 긴 코드·해설까지 한 화면 보장은 어려움 | S |
| B. 넓은 창의 2열 집중 배치 | 왼쪽 문제·코드, 오른쪽 선택지, 공통 하단 행동 | 읽기·선택·다음을 동시에 볼 수 있음 | 기존 880px 중앙 폭 확대와 긴 한글 줄바꿈 검토 필요 | M |
| C. 풀이와 회차 결과를 별도 패널로 | 풀이 중에는 문제·답·이동, 채점 후에는 요약·오답·실습 이동 | 화면마다 목적이 명확해짐 | 결과↔문제 이동·초점·현재 위치 복구 필요 | M |

**추천 조합:** 일반 퀴즈는 A부터, 코드 장면이 있는 프로그래밍 퀴즈는 B를 시안으로 비교하고, 큰 결과 카드 대신 C의 결과 패널을 검토하는 것입니다. 한꺼번에 전부 바꾸기보다 첫 문항·마지막 문항·채점 후 세 상태를 비교한 뒤 선택하십시오.

개념적인 B안 배치는 다음과 같습니다. 확정 시안이 아니라 공간 역할을 보여주는 초안입니다.

```text
수업 나가기   수업명                       저장 · 손들기
                 개념 | 퀴즈 | 실습

문제 2/5       [1] [2] [3] [4] [5]     답변 상태 표시
┌──────────────────────┬──────────────────────┐
│ 현재 문제            │ 선택지 ①             │
│                      │ 선택지 ②             │
│ 코드 / 상황 장면     │ 선택지 ③             │
└──────────────────────┴──────────────────────┘
이전 문제         힌트 보기                 다음 문제
```

번호 칩은 좁은 창에서도 44px 조작 영역을 유지하고, 미답변·답변·해결 상태를 접근 가능한 이름과 표시로 남길 수 있습니다. 글자 크기를 줄이는 것이 목적은 아닙니다. 2열이 답을 지나치게 줄바꿈시키는 폭에서는 1열로 돌아가야 합니다.

마지막 문항의 ‘다음’ 자리에는 답변 상황에 맞는 결과 확인·미답변 이동을 놓으면 주행동을 찾기 쉽습니다. 현재 `이번 문제 결과 확인`은 실제로 이번 회차의 여러 답을 채점하므로 `이번 회차 결과 확인` 또는 `전체 답 확인`이 더 정확합니다. **문항별 즉시 채점이나 선택 즉시 자동 이동은 이번 제안에 포함하지 않습니다.** 현재 전체 회차 정책을 유지할 수 있습니다.

### Q3. 채택할 때의 완료 조건

- 합의한 기본 창, 예를 들어 1280×720·100% 배율에서 대표 문항의 문제·모든 선택지·주행동이 함께 보입니다.
- 첫 문항·마지막 문항·오답·모두 해결·힌트 열림·조회/저장/채점 실패를 별도로 확인합니다.
- 좁은 창·200% 확대·긴 문구에서는 자연스러운 세로 스크롤을 허용하며 정보를 자르지 않습니다.
- 방향키·Tab·재도전 뒤의 현재 문항과 초점, 답안 보존과 이전 결과를 유지합니다.
- 일반·프로그래밍 두 퀴즈의 문항 이동·번호 상태·결과 행동부터 맞춥니다. 콘텐츠까지 범용 엔진으로 통합하지 않습니다.

### 수업 실습까지 같은 무스크롤 목표를 적용하지 마십시오

1280×720 프로그래밍 실습에서 iframe은 y=619에 시작하고 높이 660px입니다. 문서 전체는 1,834px였습니다. 목표·미션·작업실·검증을 모두 담기 때문에 퀴즈처럼 전부 한 화면에 넣는 것은 적절하지 않습니다. [캡처](consulting-20261008/programming-practice-1280x720.png)

대신 **작업에 들어간 뒤에는 작업실·실행·검증을 가깝게 보는 집중 모드**를 대안으로 검토할 수 있습니다. 현재 ‘넓게 보기’는 main 최대 폭 제한을 풀지만, 1280px에서는 켜기 전후 iframe 폭이 모두 1,231px로 같습니다. 작은 창에서 버튼을 숨기는 S안과 주변 탐색·안내를 접고 작업 공간에 진입시키는 M안이 있습니다. 기존 iframe과 작품을 유지하고 나가기·저장 실패·도움 요청을 계속 접근 가능하게 해야 합니다.

샌드위치 실습은 이번 1280×720 기본 배치에서 그림·준비 안내·입력·실행을 함께 확인했습니다. 한 명령의 합성 응답 후에도 입력 초점을 유지했고 대화는 내부 스크롤을 사용했습니다. 이 부품에 다시 안내·상태 카드를 계속 추가하는 것은 오히려 공간을 해칠 수 있습니다. 실제 AI 응답 품질을 이 합성 검사로 판단하지 않았습니다.

## 6. 추가로 확인한 개선점

### O1. 안전한 장애 분류 근거가 필요합니다 — 코드 확인, S~M

[http.ts의 failure](../../src/lib/server/http.ts)는 예상하지 못한 오류를 공통 503으로 반환합니다. 해당 경로에 애플리케이션의 오류 분류·요청 ID 기록은 없습니다. 사용자에게 원문 오류를 노출하지 않는 것은 맞지만 운영자가 원인을 나눌 단서도 약합니다.

요청 ID·작업명·안전한 오류 분류·시각 정도를 남기는 작은 방식을 검토하십시오. 오류 원문·요청 본문·학생 자료·자격 증명을 통째로 로그에 넣을 필요는 없습니다. 플랫폼의 모든 로그가 없다는 뜻이나 대형 관측 도구를 구매해야 한다는 제안은 아닙니다.

### O2. 디자인 기준과 구현이 일부 어긋납니다 — 실측·문서 대조, S

[DESIGN 262줄](../DESIGN.md)은 901~1439px·높이 800px 이하의 샌드위치 SVG 최대 높이를 190px로 적습니다. [실제 CSS 184~185줄](../../src/components/student/review/studio.module.css)은 같은 조건에서 300px이고 이번 1280×720 측정도 300px입니다. 활성 참고 계획에도 190px이 남아 있으며 후속 정정은 찾지 못했습니다.

**300px이 잘못됐다고 판단하지 않습니다. 문서가 구현과 동기화되지 않았다는 지적입니다.** 현재 화면이 합의된 결과라면 기준 문서를 맞추는 편이 옳습니다. 문서 수를 늘리기 전에 이런 숫자·상태의 동기화를 관리해야 합니다.

### O3. 공통 색의 복제는 소수 의미부터 정리하면 됩니다 — 코드 확인, 후속 S~M

CSS의 `#376fc8`은 25파일 112회, `#526173`은 21파일 139회 등장합니다. 공통 토큰은 이미 있으므로 새 디자인 시스템을 만드는 제안은 아닙니다. 주요 행동색·보조 본문색처럼 **같은 의미로 쓰는 값만 기존 변수에 연결**하는 안이 적절합니다. 단계·교사 로그인·실습 재료의 의미 있는 색까지 기계적으로 통일하지 마십시오.

### O4. 문서와 검사는 더 나누기보다 찾는 비용을 줄이십시오 — 코드 확인, 후속 S

현재 기준 문서 5개와 README는 역할이 분명하지만 같은 기능의 파일럿·확정·구현·공개 설명이 여러 곳에서 반복됩니다. README의 상태 요약은 짧게 두고 현재 결과는 HANDOFF, 정책은 PRD, 표현은 DESIGN으로 연결하는 원칙을 계속 적용하는 것이 낫습니다.

검사도 `interface-polish`, `ui-*-refinement`처럼 작업 회차 이름과 기능 이름이 섞여 있습니다. 새 사람이 어떤 변경에 어느 검사를 선택할지 찾기 어렵습니다. 해당 영역을 수정할 때 소유 기능 중심으로 정돈하는 안을 권합니다. 권한·저장 실패·경합·IME·초점·iframe 검사를 단순히 ‘많다’는 이유로 없앨 근거는 없습니다.

### O5. 장기간 사용하는 일정은 지난 항목과 등록을 정리할 수 있습니다 — 코드 확인·가설, 후속 S~M

전체 일정은 날짜 오름차순이고 지난 일정도 목록에 남으며 등록 폼은 그 뒤입니다. [schedule.tsx](../../src/components/dashboard/schedule.tsx) 사용 기간이 길어지면 오늘 일정과 등록을 찾는 이동이 늘 수 있습니다.

오늘 이후를 기본으로 보여주고 지난 일정은 펼치게 하거나, 상단 `일정 등록`으로 폼을 여는 안이 있습니다. 작은 대안은 오늘/등록 앵커입니다. 일정에 맞춰 수업을 자동 공개하거나 제출을 제한하는 기능은 현재 안내용 일정 정책과 별도입니다.

### O6. 퀴즈가 평가로 확장되면 정답 데이터 경계를 다시 결정하십시오 — 코드 확인, 미래 정책

운영 클라이언트가 사용하는 prototype 데이터 모듈에는 `correct` 필드가 있습니다. 실제 번들의 모든 정답 노출 경로를 정밀 검증한 것은 아니고, 서버 채점이나 권한 우회가 입증된 것도 아닙니다. 현재 학습용 기능을 보안 결함이라고 단정하지 않습니다.

앞으로 점수를 성적·시험에 사용한다면 공개 문항과 서버 정답 데이터의 경계를 별도 검토해야 합니다. 지금의 공통 데이터 재배치 시 이 역할을 분명히 해두는 것은 유용합니다.

## 유지해야 할 것과 당장 하지 말 것

**유지:** 단일 저장 소유자, 입력 보존, 충돌 비교, 이전 제출본 보존, 검증과 제출 구분, 자유로운 단계 이동, 응답 후 초점 복구, 화면별 CSS, 선택한 반 맥락, 로컬 합성 검증 경계.

**당장 권하지 않음:** 마이크로서비스, frontend/backend 저장소 분리, 범용 수업 플러그인 엔진, 전역 상태관리 도구 추가, 모든 부품의 Atomic Design 이동, 전체 CSS 전환, 보관함 즉시 분리, 모든 조회의 실시간화, 모든 화면의 스크롤 금지.

Ponytail 복잡도 감사에서 보수적으로 확인한 삭제 후보는 미사용 학생 CSS·사용하지 않는 2줄 재export·중복 브랜드 규칙입니다. `net: -34 lines, -0 deps possible`는 실제 패치나 화면 검증을 완료한 수치가 아니라 후보 추정입니다. 이보다 중요한 효과는 줄 수 감소가 아니라 변경할 위치를 분명히 하는 것입니다.

## 검토 방법·범위·한계
