## 1. 대시보드와 프로그래밍 개념

### 제목·진도

- `src/lib/classroom/programming-lesson.ts`의 제목을 「프로그래밍의 기초」로 바꿉니다. 강아지는 실습 소재로 유지합니다. `programming-13`·문항 ID·완료 조건·기존 작품의 연결은 유지합니다.
- `learning-overview.tsx`의 안내 details와 `learning-overview.module.css`의 전용 규칙을 제거합니다. `필수 활동 n/m개 완료`와 정규 수업 기준의 접근성 설명은 유지합니다.
- `ActivityProgressRing`의 합산 진도와 SVG 장식을 분리합니다. 실제 완료 개수가 0이고 분모가 있을 때만 12시 시작 위치에 **약 5°의 짧은 색 구간**을 표시합니다. 이 표시는 진행값·aria-valuenow·범례/툴팁 값에 반영하지 않습니다. 일부 완료나 100%에서는 실제 값으로 그립니다.
- 같은 원형을 사용하는 학생 메인·수업 격자, 교사 반 전체·학생 격자에 일관되게 적용합니다. 분모 0·초기 조회·실패의 기존 표시 경계는 유지합니다.

### 세 용어

첫 개념 ‘컴퓨터에게 전하는 말’의 블록/텍스트 실행 예시 곁에 다음 설명을 붙입니다. 새 다섯 번째 개념이나 필수 평가 항목을 만들지 않습니다.

| 용어 | 학생에게 보여 줄 설명 |
| --- | --- |
| 프로그래밍 | 컴퓨터가 할 일을 생각하고, 명령을 만들어 실행해 보며 고치는 과정이에요. |
| 프로그래밍 언어 | 컴퓨터가 할 일을 표현할 때 사용하는 약속된 언어예요. 엔트리의 블록이나 파이썬의 글자로 명령을 나타낼 수 있어요. |
| 프로그램 | 컴퓨터가 할 일을 순서와 규칙에 맞게 적어 놓은 명령의 모음이에요. |

관계 문장: **프로그래밍 언어로 명령을 표현해 프로그램을 만드는 과정이 프로그래밍이에요.** 현재 인사말 예시의 명령 묶음이 프로그램이고, 그것을 만들고 시험하는 활동이 프로그래밍임을 연결합니다. 기존 관찰 질문·블록/텍스트 전환·실행·정답 확인은 유지합니다. 운영 수업과 공용 개념을 사용하는 공개 프로토타입 모두 확인합니다.

## 2. 추상화 — 맛보기에서 처방전까지

### 필수 맛보기와 탐색

- 워크북 진입 조건은 기존 `tutorialDone`입니다. 선택 막대를 삭제하고 완료 전에는 맛보기만, 완료 뒤에는 저장된 워크북 단계를 표시합니다.
- 이미 `tutorialDone=true`인 작품은 바로 이어갑니다. false인데 `view=workbook`인 옛 작품은 current/goal/conditions/core/noise/plans와 원래 step을 유지하며 맛보기를 먼저 표시합니다. 완료한 뒤 원래 step으로 돌아가고 기존 제출·완료를 초기화하지 않습니다.
- 필수 맛보기는 현재의 상태→조건→정보 구분→결과 네 단계를 거쳐 마지막 ‘실전 워크북 시작’에서 완료를 저장합니다. 상태·조건을 고르고 핵심/노이즈 구분을 체험하는 원작 흐름과 피드백을 맞추며, 새 정답 통과 기준이나 채점은 만들지 않습니다.
- 워크북의 1~4 단계 선택 막대는 삭제하고 ‘이전 단계/다음 단계’를 유지합니다. `Step 1/4 · 나의 문제 해결 워크북`은 글자 굵기와 대비를 조금 높입니다. 이동 후 새 제목에 Effect로 초점을 옮기며 현재 입력을 먼저 확정합니다.
- ‘맛보기 필수’는 이 실습 내부의 순서입니다. 공통 개념/퀴즈/실습 탭의 자유 이동 정책은 유지합니다.

### 네 단계의 추상화 닥터

- 원작처럼 상단 닥터 제목, 중앙 대화 이력, 하단 입력/전송으로 구성합니다. 대화가 없어도 닥터의 첫 안내가 있는 충분한 높이의 대화창을 표시합니다. 단계별 추천 조작은 대화창을 밀어내지 않게 배치합니다.
- 단계별 history·입력 초안·대기·실패를 기존 UI 상태로 재사용합니다. 1→2→3→4와 이전 이동에서 해당 단계의 대화를 다시 읽을 수 있게 합니다. 상담 전문을 Firestore/서버에 새로 저장하지 않습니다.
- 긴 대화는 중앙 영역만 스크롤하고 입력/전송은 보입니다. 하단을 읽던 학생에게만 새 응답을 따라가며, 과거 대화를 읽는 중에는 위치를 유지합니다. Enter 전송·Shift+Enter 줄바꿈·한글 조합 Enter·중복 요청 차단을 확인합니다.
- 모든 단계에서 현재 상태/목표/조건/핵심/계획에 맞는 상담을 보냅니다. 단계 이동과 AI 응답의 시점이 달라도 다른 단계의 대화에 잘못 붙이지 않습니다.

### Step 3: 요소 제안과 버리기

- Step 2에서 처음 비어 있는 요소 목록을 만들 때 `AI로 요소 만들고 다음`이라는 명시적 버튼을 사용합니다. AI는 현재 상태·목표·조건을 바탕으로 학생이 문제 상황에서 관측할 수 있는 **7개**의 짧은 요소를 제안합니다. 기존 서버의 정확히 7개 규격은 요청한 6~8개 범위를 충족하므로 유지합니다.
- 프롬프트는 구체적이고 서로 다른 요소, 중요한 정보와 판단해 볼 주변 정보를 함께 제안하도록 다듬습니다. 공백을 제외하고 비어 있지 않은 서로 다른 7개인지 확인하며, 중복/빈 후보 응답은 기존 목록을 보존하고 재시도를 안내합니다. 모든 요소를 이미 정답/노이즈로 분류해서 주지 않습니다. 예시 고정 단어를 실제 제공자 실패의 대체 결과로 넣지 않습니다.
- 처음 생성한 7개는 모두 남김 목록에 둡니다. 단어 클릭은 해당 단어 하나만 core→noise로 옮기며, 다시 클릭하면 되돌립니다. 임의의 나머지 단어를 자동으로 버리거나 초기화하지 않습니다.
- 후보 위치는 기존 adopted의 core/noise 기록 순서에서 현재 core+noise에 존재하는 값만 중복 제거해 복원합니다. 새 7개는 한 번에 같은 순서로 기록하고, 버림/복구 때 adopted를 바꾸지 않습니다. 기록에 없는 직접 입력 요소는 뒤에 유지합니다. 과거 데이터에 저장되지 않은 원래 생성 순서를 새로 복원했다고 주장하지 않습니다.
- 이미 요소가 있으면 ‘다음 단계’로 이어갑니다. 재추천은 후보를 보여 주고 학생이 선택해 더하도록 하며 현재 요소·분류·직접 입력을 자동 대체하지 않습니다. 저장 한도와 adopted 100개 한도는 유지합니다.
- ‘비어 있는 요소/계획’은 최초의 길이 0 배열을 뜻합니다. 학생이 추가한 `[""]` 같은 미완성 항목도 기존 입력으로 보존하며 자동 생성으로 대체하지 않습니다.
- AI 호출은 최신 step=3 초안을 controller.update로 만든 뒤 기존 requestAi의 저장/flush 흐름을 통해 요청합니다. 대화 기록의 요청 단계는 getDraft 또는 명시적 requestedStep으로 고정해 옛 렌더의 step=2를 사용하지 않습니다.

### Step 4: 처방전

- 원작처럼 **문제 상태 정의(현재·조건·목표) → 생각 다이어트(버림·남김) → 실천 계획 3~5단계 → 닥터 상담/결과 공유** 순서로 구성합니다. 각 계획은 남긴 핵심과 목표/조건을 구체적으로 사용해야 합니다.
- 계획이 비어 있으면 Step 3의 `AI로 처방전 초안 만들기`를 눌러 기존 abstraction-plan 요청을 보냅니다. 성공한 3~5개를 편집 가능한 초안으로 표시합니다. 버튼이 AI 초안 작성임을 분명히 알리고 작품 검증·제출은 별도 조작으로 유지합니다.
- 이미 작성한 계획이 있으면 기존 내용으로 처방전을 엽니다. 재추천은 현재 계획을 보존한 채 후보로 보여 주고 선택 추가/채택합니다. AI 응답 대기 중 새 편집·다른 요청·재진입으로 내용이 달라지면 옛 결과를 작품에 적용하지 않습니다.
- 현재/목표·조건·핵심/노이즈·번호 계획을 직접 수정하고, 수정 결과로 복사/인쇄합니다. 원작의 후속 행동/계획 영역을 현재 상태 요약만으로 대체하지 않습니다. 기존 제출과 교사 확인, 추상화 정의를 순서도에 선택 복사하는 경계도 유지합니다.
- 실패 때 입력·선택·계획을 보존하고 같은 위치에서 명시적으로 재시도합니다. 기존 상태를 확인/수정하며 이전 단계로 돌아갈 수 있게 하며, 자동 재호출·무관한 임시 정답·자동 제출은 하지 않습니다.

## 3. 순서도 — V1 작업실의 조작과 밀도

### 배치와 크기

- 실습 상단 다섯 단계와 기획서→세로 기호 보관함→캔버스→실행 과정의 읽기 순서를 유지합니다. 현재도 이 구조가 있어 새 작업실을 다시 만들 필요는 없습니다.
- V1 최종 CSS 기준은 펼친 기획서 240px·팔레트 100px·실행 과정 220px, 접힌 실행 과정 40px입니다. 앞부분의 대체된 기본 폭을 그대로 복사하지 않습니다. 넓은 창에서는 이를 기준으로 맞추고 낮은/좁은 창에서는 캔버스와 조작을 우선합니다.
- 현재 `100dvh - 355px`(집중 모드 -245px)로 제한된 작업실을 실제 남은 창 높이에 맞춥니다. V1의 `100vh - 150px`는 원작 헤더의 값이므로 CS Class에 그대로 넣지 않고 LessonShell·단계 탭의 실측 높이를 사용합니다. 반복 여백·헤더 높이·과도한 둥근 카드 장식을 줄여 캔버스를 확보합니다.
- 기본 폭에서도 주요 조작을 찾을 수 있게 만들고 넓게 보기/집중 모드에서 원작의 작업 밀도에 가깝게 확장합니다. 기획서·팔레트·실행 과정은 필요한 영역만 내부 스크롤합니다.

### 실행 과정과 실행바

- 오른쪽은 위의 흰 변수표(변수·현재값·직전값)와 아래의 어두운 출력 콘솔로 분리합니다. 원작의 빈 상태 안내·실행 추적·지우기·접기를 현재 실행 데이터로 표현합니다. 입력/분기 질문은 해당 실행 기호 곁에 둡니다.
- 자유 캔버스 하단 실행바는 원작의 알약 형태·끌기 손잡이·실행/일시정지·한 단계·초기화·상태 표시를 맞춥니다. 속도는 자유 공방에서 `1× → 2× → 0.5×` 순환 버튼으로 맞추고 퍼즐·예시의 기존 조작은 별도 변형으로 보존합니다.
- 출력 지우기나 실행 초기화가 작품 기호·연결·기획서를 삭제하지 않게 합니다. 실행 중 편집·중지·다시 실행의 기존 상태 전환을 유지합니다.

### 하단 편집 패널 제거와 직접 조작

- `키보드 편집 · 기호와 연결 설정` details·전용 스타일·상태/ref를 삭제합니다. 별도의 큰 대체 패널은 만들지 않습니다.
- 기존 캔버스의 F2/연필 문구 편집, 방향키 이동, Delete/휴지통 삭제, Tab+Enter 포트 연결, 연결선 Enter/Delete 조작을 그대로 활용합니다. 필요한 편집 되돌리기는 캔버스 상단의 작은 버튼으로 옮깁니다.
- 구조 오류의 ‘해당 기호로 이동’은 없어진 inspector 대신 실제 SVG 기호/연필/편집 입력으로 초점을 연결합니다. 열려 있던 패널 제거로 사라진 대상을 초점 복귀 위치로 사용하지 않습니다.
- 팔레트 클릭/끌기 추가, 포트 연결 미리보기, 연결 가능/불가능 안내, 점선 캔버스 빈 곳 이동, 드래그 휴지통을 원작 순서로 확인합니다. 입력 포트에서 연결 시작 금지·사용 중인 출구 보호·시작/종료 중복 보호·예/아니오 의미는 유지합니다.
- 논리 개선은 잘못된 연결을 막는 이유, 분기 경로와 학생이 다음에 할 행동을 더 명확하게 하는 범위로 제한합니다. 원작 전역 상태·인증·운영 Firebase·띵커보드·평가 코드를 옮기지 않습니다.

## Global Constraints

- 기존 미커밋/미추적 변경과 로컬 학습 기록을 보존합니다. reset/clean/checkout으로 작업을 초기화하지 않습니다.
- 수업 ID·문항 ID·기존 개념 4개·진도 분모·정답·이전 제출/완료를 유지합니다. 제목 변경과 0% 장식은 계산/채점을 바꾸지 않습니다.
- 저장 소유자는 기존 useWork입니다. UI가 별도 답안 저장 writer가 되지 않습니다. 실패·revision 충돌·수정 중 AI·늦은 응답·임의 직접 입력을 보존합니다.
- AI는 학생이 알 수 있는 명시적 조작으로 요청합니다. 모델·제한·타임아웃·중복/캐시 정책·상담 전문 비보관을 유지합니다. 프롬프트 변경 시 promptVersion을 갱신해 옛 캐시와 구분합니다.
- tutorialDone과 adopted를 재사용하고 새 저장 필드·수집 항목·라이브러리를 추가하지 않습니다. 배열 순서의 과거 미저장 정보는 임의 추정하지 않습니다.
- 화면별 CSS를 담당 컴포넌트 옆에 둡니다. LessonShell·학생 저장/이탈 보호·교사 체험의 권한/메모리 경계를 유지합니다.
- 실제 API·라이브러리를 구현/설정할 단계에 관련 Next 로컬 안내와 설치 버전 Context7 문서를 확인합니다. 이번 계획은 새 API/의존성 구현을 하지 않습니다.
- 검사는 demo-cs-class·Auth9099/Firestore8080·localhost:3000만 사용합니다. 운영 학생/작품·운영 AI 호출·반 설정 변경은 계획 검증에 쓰지 않습니다.

## Review Focus

1. tutorialDone=false인 옛 워크북: 맛보기 완료 후 원래 step·초안·이전 제출로 돌아와야 합니다(회차 2).
2. AI 요청 중 단계/작품 변경: 요청 단계의 대화에만 붙고 현재 입력·단어·계획을 덮지 않아야 합니다(회차 3).
3. 한글 조합·긴 대화·과거 읽기 위치: 네 단계 모두 입력을 보존하고 대화창 안에서 읽어야 합니다(회차 3).
4. 키보드만으로 순서도 조립: inspector가 없어도 문구·포트·선 삭제·오류 이동·되돌리기가 가능해야 합니다(회차 5).
5. 낮은/좁은 창·초기 조회: 시작점 장식이 실제 진도로 오인되지 않고 캔버스/전송/실행 버튼을 가리지 않아야 합니다(회차 1·3·4).

## 검사 실행 기준

반복 수정 중에는 `npm.cmd run typecheck`와 대상 Playwright 파일을 우선합니다. 에뮬레이터가 실제 실행 중일 때만 다음 예처럼 대상 인자를 앱 검사에 전달합니다.

```powershell
npm.cmd run test:e2e:running -- tests/review-abstraction-v1-ux.spec.ts
npm.cmd run test:e2e:running -- tests/review-flowchart-studio-fixes.spec.ts
npm.cmd run test:review
```

에뮬레이터가 꺼져 있으면 대상 Playwright 명령을 `firebase emulators:exec` 안에 둡니다. 정확한 캐시·Java·fixture 준비는 [개발 안내](../DEVELOPMENT.md)를 따릅니다. 최종 통합은 단일 worker·단일 실행으로 하고 검증 실패를 허용오차/시간 제한 확대·활동 수 축소로 숨기지 않습니다.

## 계획 작성 때 확인한 범위

계획 작성 시 코드·미커밋 diff·관련 검사·활성 문서와 V1 원문을 읽고 대시보드/프로그래밍·순서도·추상화를 나누어 대조했습니다. 원작 캡처와 주석은 목표 UX의 근거이며 당시 앱 수정·운영 답안/AI/저장/시드는 실행하지 않았습니다. 이 문단은 계획 작성 당시의 범위이고 이후 승인된 구현·검사·병합·배포의 현재 결과는 [HANDOFF](../HANDOFF.md)에서 확인합니다.
