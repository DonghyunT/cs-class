## 1. 범위와 전제

### 1.1 사용자가 정한 것(바꾸지 않음)

- 범위는 보고서 §13.2의 1~4단계 전부입니다. 5단계는 제외합니다.
- 퀴즈 정오는 지금처럼 회차를 다 푼 뒤 보여 줍니다. 오답에도 이유를 붙이되 재도전 전에는 정답·정답 규칙을 밝히지 않습니다.
- 재도전은 같은 문항입니다. 분량은 유지합니다.
- 1024px 가로 화면은 반드시 지원합니다. 768px 세로는 필수가 아니지만 작업이 불가능해지는 일은 피합니다.
- 반영: 작업 브랜치에 단계별 커밋, 마지막에 브랜치 push까지만 합니다. PR·병합은 하지 않습니다.
- 검증: 단계마다 Tier 1~2와 선별 E2E, push 직전 로컬 전체 E2E 1회(사용자 승인 완료). GitHub 수동 실행은 하지 않습니다.
- 운영 서버·운영 데이터는 조회도 쓰기도 하지 않습니다. 모든 실행은 `demo-cs-class` 에뮬레이터에서 합니다.

### 1.2 지키는 규칙

- **저장 계약:** 이번 변경은 `useWork`를 건드리지 않습니다. 새 저장 항목·자동 저장 타이머를 만들지 않습니다. 피드백은 기존 저장 예외 행동(`check-concept`·`grade-quiz`)의 응답 문구만 바뀝니다. S1-4는 저장하지 않고 화면에서만 계산합니다.
- **선택지 고정:** 기존 개념 확인·퀴즈 문항의 선택지 수·순서·정답 번호를 바꾸지 않습니다(보고서 §11.3). 문항 지문·힌트·피드백 문구만 바꿉니다.
- **고정 자료 불변:** `tests/fixtures/entry-legacy-keys.json`·`entry-legacy-objects.json`을 다시 만들거나 고치지 않습니다. 고정 자료 검사가 실패하면 코드를 고칩니다.
- **운영 데이터 이전 없음:** 이미 저장된 `quizFeedback`·`conceptFeedback` 문구는 그대로 둡니다(옛 문구가 남는 한계는 HANDOFF에 기록).
- **반영 경로 메모:** 공통 화면·서버 채점 데이터·고정 자료 인접 코드를 바꾸므로 [DEVELOPMENT §2.1](../DEVELOPMENT.md#위험도별-반영-경로) 기준으로는 PR 경로입니다. 이번에는 사용자 결정에 따라 브랜치 push에서 멈추고, `main` 반영은 나중에 PR 경로로 합니다.
- **새 라이브러리 없음.** 엔트리 내부 함수는 존재 검사 뒤에만 씁니다(DEVELOPMENT §4.1).

## 4. 1단계: 학생을 막는 결함

### S1-1 그린 선이 실행 뒤에도 남게 하기

- **목적:** 정사각형을 실행하면 0.3초 안에 선이 사라짐(보고서 §12.3 가1, 원칙 10).
- **원인 [코드·재현·총괄]:** `public/entryjs/workspace.js`의 실행 감시기는 모든 실행 코드가 비면 `if (!waitsForEvents) void stop("finished")`로 `Entry.engine.toggleStop()`을 부릅니다. 엔트리의 정지 처리는 그린 선을 지웁니다(C-1). 이벤트 줄이 있으면 멈추지 않고 `result("finished")`·`waiting`을 보낸 뒤 학생의 '정지하기'를 기다립니다.
- **바꾸는 방식(최소):** 붓 블록이 있는 실행도 이벤트 대기와 같은 길로 보냅니다.
  - `workspace.js`: `EVENT_STARTS` 옆에 `DRAW_BLOCKS = ["start_drawing", "start_fill"]`(도장은 정지해도 남아 제외, C-1). `run` 이벤트에서 `waitsForEvents`와 함께 `keepsDrawing`(어느 오브젝트 코드에 붓 블록이 있는지, C-2의 API)을 계산합니다. 감시기 조건을 `if (!waitsForEvents && !keepsDrawing) void stop("finished"); else if (!reported) { result("finished"); reported = true; send("waiting", { drawing: !waitsForEvents }); }`로 바꿉니다. 대기 중 시간은 이미 15초 제한에서 빠집니다(`waitingIdle`).
  - `entry-practice-workspace.tsx`: `waiting` 메시지에 `drawing`이 참이면 그리기 안내를, 아니면 지금의 이벤트 안내(`WAITING`)를 결과 줄 끝에 붙이고, `waiting-ended`는 두 안내 모두 떼어 냅니다. 새 상태 체계는 만들지 않고 기존 결과 줄(`role="status"`)만 씁니다.
- **검증이 막힌 이유 [코드]:** 대기 중에는 `running`이 참이라 '조건 검증'·'작품 제출'이 비활성인데(`entry-practice-workspace.tsx` 306·309행), 지금 이벤트 안내 `WAITING`(23행)은 "다 해 봤으면 무대 아래 ‘정지하기’를 눌러 주세요."까지만 말하고 검증과의 관계는 말하지 않습니다. 두 안내 끝에 같은 한 문장을 더합니다.
- **학생 문구(결과 줄 끝에 붙는 안내):**
  - 그리기(새): " 그린 결과를 다 봤으면 무대 아래 ‘정지하기’를 눌러 주세요. 정지하면 무대가 처음 상태로 돌아가고, 그다음 조건을 검증할 수 있어요."
  - 이벤트(지금 문구 + 한 문장): " 키를 누르거나 오브젝트를 클릭해 보세요. 다 해 봤으면 무대 아래 ‘정지하기’를 눌러 주세요. 정지하면 조건을 검증할 수 있어요."
  - `tests/programming-classroom.spec.ts` 565·570행은 앞 문장을 포함 여부로만 보므로 그대로 통과해야 합니다.
- **영향:** 그리는 미션(정사각형·정다각형, 교사 제출 작품 실행기 포함)은 끝나도 '정지하기' 상태로 남아 '조건 검증'이 정지 전까지 비활성입니다(지금 이벤트 미션과 같은 동작). 엔트리봇과 선은 끝난 상태로 남았다가 정지하면 처음 상태로 돌아갑니다. 말한 내용은 지금처럼 결과 줄의 '마지막 말'로 남습니다(정지가 말풍선도 지움, C-1).
- **문서:** DESIGN §5.1에 '실행 결과 유지' 한 줄, DEVELOPMENT §4.1 '실행·이벤트' 항목에 붓 블록 대기를 더합니다(초안: 이 계획 §10.1).

### S1-2 기초 미션 1 힌트를 검증 블록에 맞추기

- **목적:** 힌트는 '말하기', 검증은 `dialog_time`('( )을(를) ( )초 동안 말하기')만 인정(가2, 원칙 2).
- **사실 [코드]:** `programming-entry.ts` 11행 name `hint`가 화면 힌트이자 채점 실패 문구입니다(`programming-grader.ts` 230행 부근 `fail(mission.hint)` 두 곳). 이 문구는 `tests/fixtures/entry-legacy-keys.json`의 `checks`에 고정돼 있습니다.
- **바꾸는 방식:** `ProgrammingMission`에 선택 필드 `failure?: string`(채점 실패 문구)를 더하고 채점기 두 곳을 `fail(mission.failure ?? mission.hint)`로 바꿉니다. name 미션만 `failure`에 옛 문구를 옮기고 `hint`를 새로 씁니다. 다른 미션은 그대로라 고정 자료가 바뀌지 않습니다. 평균 미션 위 주석을 "name·multiply·average·move·keys의 실패 문구는 고정 자료가 지키므로 바꾸려면 `failure`에 옛 문구를 남긴다"로 고칩니다.
- **학생 문구:**
  - 새 `hint`: "질문 다음에 ‘( )을(를) ( )초 동안 말하기’(팔레트에서는 ‘안녕! 을(를) 4 초 동안 말하기’)를 연결하고, 그 안에 ‘대답’을 넣어 보세요." 괄호 안 팔레트 모양은 C-4로 확인한 대로 씁니다. 안내=채점 단위 검사는 ‘’로 인용한 `BLOCK_LABELS` 표기 기준 그대로이며, 팔레트 모양 인용('안녕! 을(를) …')은 `BLOCK_LABELS`에 없어 검사 대상이 아닙니다.
  - `failure`(옛 문구 그대로): "질문 다음에 말하기를 연결하고, 말하기 안에 ‘대답’을 넣어 보세요."
- **문서:** DEVELOPMENT §4.1 '수업별 미션'과 '정규화·복제 제약'의 "미션 힌트로 대신합니다"를 `failure`(없으면 `hint`)로 고칩니다.

### S1-3 1024px에서 작업실 전체가 보이게

- **목적:** `.frame{min-width:1000px}` 때문에 1024px에서 오른쪽이 잘림(가3, 원칙 11).
- **사실 [코드]:** `entry-practice-workspace.module.css` 12행. 바깥 `.frameScroll`은 `overflow-x:auto`라 영역 안에서만 가로로 밀리고, 1024px에서 쓸 수 있는 폭은 본문 여백(16px×2)·테두리·스크롤바를 빼면 약 980px입니다 [추정, C-3에서 실측]. 무대 크기는 `workspace.js`의 `stage-size` 메시지로 600px 이하에서만 엔트리 최소 무대(324px)로 줄입니다.
- **바꾸는 방식(C-3 실측으로 수치 결정):**
  1. `.frame`의 `min-width`를 1024px에서 남는 폭 이하로 낮춥니다(예상 960px).
  2. 그 폭에서 블록 조립판이 300px보다 좁아지면 `entry-practice-workspace.tsx`의 `matchMedia("(max-width: 600px)")` 기준을 넓혀 1024px 부근에서도 작은 무대를 씁니다(예상 1100px). 엔트리 좌표는 그대로이고 무대 표시만 작아집니다.
  3. 768px은 영역 안 가로 스크롤로 조립판에 닿을 수 있는지만 확인하고, 막히면 기록합니다(필수 아님).
- **통과 기준:** 1024×768·1280×720에서 페이지와 작업실 영역 모두 가로로 밀리지 않음(`scrollWidth - clientWidth ≤ 1`), 무대·팔레트·조립판이 iframe 안에 다 보이고 조립판 300px 이상, '시작하기'·'오브젝트 추가하기'가 보임. 1544×712의 기존 배치 검사(`ui-workspace-refinement.spec.ts`)도 통과.
- **문서:** DESIGN §5.1 'EntryJS 작업실 크기'의 1,000px·600px 수치와 §2.3에 '학교 기기 폭' 한 줄(초안: 이 계획 §10.1).

## 5. 2단계: 피드백

공통 기준(보고서 §5, §13.1 원칙 3·4, §13.3): 오답 문구는 1~3문장으로 '고른 답이 왜 맞지 않는지(값 넣기→계산, 참·거짓→실행 경로)'와 '다시 볼 곳'을 씁니다. '정답'이라는 말, 정답 보기 문구, 정답 번호, 정답을 바로 만드는 규칙을 쓰지 않습니다. 보기가 둘인 문항은 오답 이유만으로도 답이 좁혀지며, 이는 받아들이는 한계입니다(이 계획 §13의 R11).

### S2-1 퀴즈 오답을 고른 답별 이유로

- **목적:** 오답 피드백이 미리 보인 힌트와 같고, 복습은 12문항이 같은 문장(나1, §11.2 첫 행).

- **바꾸는 방식:**
  - 데이터: `programming-data.ts`·`conditionals-data.ts`·`loops-data.ts`의 각 퀴즈에 `why`(오답 보기 번호 → 문구, 키는 선택지 id 문자열)를 더합니다(부록 A-1~A-3). 복습은 서버 전용 `review-quiz.mjs`의 각 문항에 `wrong`(문항별 한 문장 묶음, 부록 A-4)을 더합니다. 복습 보기는 정의 낱말이라 고른 답별로 다르게 쓸 이유가 적어 문항별로 씁니다.

### 6.1 S3-13 문항이 묻는 새 규칙을 본문에 먼저

## 7. 4단계: 조립 안내와 원칙 문서

### S4-1 DESIGN §5.1 먼저 고치기

'미션 안내 카드' 항목의 "힌트는 한두 줄로 짧게"를 번호 조립 안내 기준으로 바꾸는 문서 커밋을 코드보다 먼저 합니다(초안: 이 계획 §10.1). 이 커밋 뒤 S4-2·S4-3이 그 기준을 따릅니다.

### S4-2 접힌 힌트 안에 번호 조립 안내

- **목적:** 꾸러미·실제 블록 이름·넣을 칸·고르는 기준·이유가 없음(가5·가6, 원칙 9, 보고서 §6).
- **바꾸는 방식:**
  - `ProgrammingMission`에 `steps: readonly string[]`를 더하고 12개 미션(name·multiply·move·keys·average·pass·freethrow·escape·square·polygon·tree·safe)에 부록 D 문구를 넣습니다. `hint`(한 줄 요약)·`failure`는 그대로라 고정 자료가 바뀌지 않습니다.
  - `programming-lesson.tsx` 124행 `<details>` 안: 요약(`hint`) 아래에 `<ol aria-label="조립 순서">`로 `steps`를 보이고, 그 아래에 기존 '검증에는 이 블록만 봐요'를 둡니다. 기본은 접힌 채입니다. 집중 모드 동작(`PracticeGuidance`)은 그대로입니다.
  - **블록 표기 규칙:** 블록 이름은 앱의 `BLOCK_LABELS` 표기('( )' 칸, '검증에는 이 블록만 봐요' 알약과 같음)로 ‘’ 안에 쓰고, 꾸러미 이름을 앞에 괄호로 붙입니다. 각 미션 안내에서 그 블록을 **처음** 언급할 때는 C-5로 확인한 팔레트 모양을 뒤에 괄호로 붙입니다. 예: "(생김새) ‘( )을(를) ( )초 동안 말하기’(팔레트에서는 ‘안녕! 을(를) 4 초 동안 말하기’)". 같은 미션 안에서 두 번째부터는 `BLOCK_LABELS` 표기만 씁니다. 안내=채점 단위 검사는 `BLOCK_LABELS` 표기 기준 그대로입니다.
- **안내=채점 검사:** 단위 검사에서 (1) `hint`·`steps`가 ‘’로 인용한 블록 이름이 `BLOCK_LABELS`에 있으면 그 미션의 `missionBlockLabels`에 들어 있어야 하고, (2) 부록 D 순서대로 만든 해답이 `checkProgrammingMission`을 통과해야 합니다(이 계획 §9.2).

### S4-3 '먼저 해볼 작은 실험'을 '만든 뒤 확인하기'로

- **바꾸는 방식:** `programming-lesson.tsx` 123~124행에서 실험 카드를 힌트 다음으로 옮기고 제목을 "만든 뒤 확인하기"로 바꿉니다. `PracticeGuidance` 이름표 "실험·블록 연결 힌트" → "블록 연결 힌트·만든 뒤 확인". `programming-lesson.module.css` 55행의 821~1339px 격자에서 `.experiment`와 `.hint`의 행을 맞바꿉니다. 작품이 있을 때만 보이게 하는 조건부 표시는 하지 않습니다(보고서 §7 '순서를 맞춘다'의 최소안).
- **경계 사례 문구(보고서 §6 표):**
  - escape: "1과 0, 0과 1, 0과 0을 넣어 보세요. 여유가 있으면 1과 1에서 어떻게 될지 먼저 예상해 보세요."
  - tree: "4번·5번·6번째 클릭에서 나무 모양을 비교해 보세요. 25번 넘게 클릭해도 나무가 처음 모양으로 돌아가지 않는지도 보세요."
  - 나머지 미션의 `experiment`는 이미 만든 뒤 확인하는 내용이라 그대로 둡니다(freethrow는 S3-9).

### S4-4 블록 이름 일치

- **바꿀 곳 [코드]:** `loops-data.ts` lc1 예시·지문, distance·pentagon 코드 줄, `concept-visual.tsx` lc1 블록 글자.

```markdown
- **EntryJS 작업실 크기:** 실제 편집기 및 무대는 최소 가로 <C-3 수치>px, 세로 660px(저해상도 620px)를 확보하며, 1,024px 가로 화면에서는 페이지·작업실 영역 모두 가로로 밀리지 않고 무대·팔레트·조립판(300px 이상)이 다 보입니다. 더 좁으면 작업실 내부 가로 스크롤을 허용합니다.

- **상태 표시:** 상태는 무엇에 대한 상태인지 말하고, 다시 들어와도 같게 보입니다. 작업실 상태 줄은 저장·검증·제출을 따로 말합니다. 저장하지 않는 실행 확인(이름 미션의 두 이름 확인)은 제출 상태와 섞지 않고, 이미 검증을 통과한 작품에 다시 들어오면 0부터 세지 않고 `서로 다른 이름 확인 완료`로 보여 줍니다. 바로 저장되는 결과와 저장 버튼이 필요한 영역의 구분은 §4.2를 따릅니다.
```

4. 위 칸에는 ‘합격’, ‘아니면’ 아래 칸에는 ‘불합격’을 말하는 (생김새) 말하기 블록을 넣어요.

**freethrow(조건 · 자유투 평가)**
1. 이 작품은 성공 개수를 한 번만 물어요. 엔트리봇에 ‘시작하기 버튼을 클릭했을 때’를 놓고 (자료) ‘( )을(를) 묻고 대답 기다리기’를 붙여요.
2. 틀부터 만들어요. (흐름) ‘만일 ( )(이)라면 / 아니면’을 붙이고, 그 블록의 ‘아니면’ 칸 안에 같은 블록을 하나 더 넣어요. 말을 넣을 칸이 위·가운데·아래 세 곳이 돼요.
3. (판단) ‘( ) 비교 ( )’로 바깥 만일의 조건 칸에 (대답 ≥ 8), 안쪽 만일의 조건 칸에 (대답 ≥ 5)를 넣어요. 큰 기준 8을 먼저 확인해야 9개가 ‘잘했어요!’로 빠지지 않아요.
4. 세 칸에 차례로 ‘훌륭해요!’, ‘잘했어요!’, ‘더 연습해 보자!’를 말하게 해요.

**escape(조건 · 도전 방탈출)**
1. ‘시작하기 버튼을 클릭했을 때’ 아래에서 1번 문제를 풀었는지(1 또는 0) 묻고, 바로 (자료) ‘변수를 ( )(으)로 정하기’로 A에 ‘대답’을 저장해요. 2번도 묻고 B에 저장해요.
2. (흐름) ‘만일 ( )(이)라면 / 아니면’을 붙여요.
3. (판단) ‘( ) 그리고/또는 ( )’의 가운데를 ‘또는’으로 바꾸고, 두 칸에 ‘( ) 비교 ( )’로 만든 (A = 1)과 (B = 1)을 넣어요.
4. 완성한 판단 블록을 만일의 조건 칸에 넣고, 위 칸에 ‘탈출 성공!’, 아래 칸에 ‘탈출 실패’를 말하게 해요.

**square(반복 · 정사각형 그리기)**
1. 엔트리봇에 ‘시작하기 버튼을 클릭했을 때’를 놓고, 아래에 (붓) ‘그리기 시작하기’를 붙여요. 이 블록이 있어야 지나간 길에 선이 남아요.
2. 그 아래에 (흐름) ‘( )번 반복하기’를 붙이고 4를 넣어요.
3. 반복 안에 (움직임) ‘이동 방향으로 ( )만큼 움직이기’(100)와 ‘이동 방향을 ( )만큼 회전하기’(90°)를 차례로 넣어요. ‘방향을 ( )만큼 회전하기’는 엔트리봇 모양까지 함께 돌리며, 어느 쪽을 써도 정사각형이 그려져요(C-8).
4. 실행이 끝나도 선은 남아 있어요. 다 봤으면 무대 아래 ‘정지하기’를 눌러요.

**polygon(반복 · 정다각형 그리기)**
1. ‘시작하기 버튼을 클릭했을 때’ 아래에 (자료) ‘( )을(를) 묻고 대답 기다리기’로 변의 수를 묻고, 그 아래에 (붓) ‘그리기 시작하기’를 붙여요.
2. (흐름) ‘( )번 반복하기’를 붙이고 횟수 칸에 ‘대답’을 넣어요.
3. 반복 안에 ‘이동 방향으로 ( )만큼 움직이기’와 ‘이동 방향을 ( )만큼 회전하기’를 넣어요.
4. 회전 각도 칸에 (계산) ‘( ) 사칙연산 ( )’을 넣어 ÷로 바꾸고, 왼쪽에 360, 오른쪽에 ‘대답’을 넣어요. 한 바퀴 360°를 변의 수만큼 나누어 돌아요.

**tree(반복 · 나무 키우기)**
1. 오브젝트 목록에서 ‘나무’를 골라요. 코드는 나무에 만들어요.
2. (시작) ‘마우스를 클릭했을 때’를 놓아요. 무대 어디를 클릭해도 실행돼요.
3. 그 아래에 (자료) ‘변수에 ( )만큼 더하기’를 붙이고 변수는 ‘클릭 수’, 값은 1로 해요.
4. (흐름) ‘만일 ( )(이)라면’을 다섯 개 이어 붙이고, 조건 칸마다 (판단) ‘( ) 비교 ( )’로 (클릭 수 = 5), (= 10), (= 15), (= 20), (= 25)를 만들어요. 클릭 수는 (자료) ‘변수 값’에서 골라요. ‘=’를 써야 그 수가 될 때 한 번만 모양이 바뀌어요.
5. 각 만일 안에 (생김새) ‘다음 모양으로 바꾸기’를 넣고, 25일 때는 ‘성공~!’을 말하는 ‘( )을(를) 말하기’도 넣어요.
(준비 단계는 넣지 않습니다. 정지하면 엔트리가 클릭 수와 모양을 처음으로 돌립니다(C-7). QA에서 다르게 나오면 그때 '시작하기 버튼을 클릭했을 때 → 클릭 수 0, 첫 모양' 단계를 더합니다.)

**safe(반복 · 도전 비밀번호 금고)**
1. 엔트리봇에 ‘시작하기 버튼을 클릭했을 때’를 놓고, 아래에 (흐름) ‘( )이(가) 될 때까지 반복하기’를 붙여요.
2. 조건 칸에 (판단) ‘( ) 비교 ( )’로 (대답 = 1234)를 만들어 넣어요. 이 조건이 참이 되면 반복을 멈춰요.
3. 반복 안에 (자료) ‘( )을(를) 묻고 대답 기다리기’로 비밀번호를 물어요. 묻기가 반복 안에 있어야 틀릴 때마다 다시 물어요.
4. 반복 블록 아래(바깥)에 ‘금고가 열렸어요!’를 말하는 (생김새) ‘( )을(를) 말하기’를 붙여요. 반복 안에 두면 틀릴 때마다 말해요.

허용 블록 확인 [코드]: 위에 인용한 블록은 `entry-palette.ts`의 `MISSION_BLOCKS`에서 각 미션에 들어 있습니다(예: multiply는 '( )을(를) 말하기'가 없어 '○초 동안 말하기'만 씀, tree는 `set_variable`·`change_to_some_shape` 포함). S4-2 단위 검사가 이를 다시 확인합니다.
